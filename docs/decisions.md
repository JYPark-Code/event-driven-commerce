## 0. 이 프로젝트가 실증하려는 이력서 경험

이력서의 다음 경험을 **직접 구현하고 측정**해서 면접에서 설명 가능하게 만드는 것이 목표다.

| 이력서 항목 | 출처(이력서) | 이 프로젝트의 실증 축 |
|---|---|---|
| Kafka 비동기 주문 처리, DLQ + 재시도, 1000 TPS 대응, 응답시간 50% 단축 | 폐쇄몰 주문 시스템(2024.05~12) | **축 1. 주문 처리** — 동기 vs Kafka 비동기 비교 측정 |
| 캐시 계층화 (CDN → Redis L2 → Caffeine L1 → MySQL), 변경 시 무효화 | 폐쇄몰 주문 시스템 캐시 플로우 | **축 2. 상품 조회 캐시 계층화** |
| Spring Batch 월별 정산, Spring Security RBAC, 특정 IP 접근 제어 | 백오피스 Java 마이그레이션(2024.12~2025.03) | **축 3. 백오피스 (RBAC + Batch)** |
| 1000 TPS 감당 웹사이트 운영 | Skills 요약 | **축 4. 부하테스트 (k6, 1000 TPS 목표)** |

핵심: 이력서엔 "성과 수치"(매출 300%, 다운타임 80% 감소 등)만 적혀 있고 **재현 가능한 측정 근거가 없다**.
이 프로젝트는 그 수치를 **내 손으로 재현·측정**해서, 면접에서 "어떻게 측정했고 병목이 무엇이었나"까지 말할 수 있게 한다.

## 1. 빌드 도구: Gradle (Groovy DSL)

- **맥락**: 빈 폴더에서 시작, 빌드 도구 미정.
- **대안**: Maven(pom.xml), Gradle Kotlin DSL.
- **선택**: Gradle Groovy DSL.
- **이유**: Spring Boot 포트폴리오에서 가장 일반적, 빌드 속도·설정 간결, wrapper로 별도 설치 불필요(팀/면접관 재현 용이). Groovy 예제가 Kotlin DSL보다 풍부.
- **트레이드오프**: Kotlin DSL 대비 타입 안정성·IDE 자동완성이 약함. 데모 규모에선 영향 작음.

## 2. 아키텍처: 모듈러 모놀리식 (단일 Spring Boot 앱)

- **맥락**: 이력서엔 Payment / Order / Notification 이 **별도 서비스(MSA)**로 기술됨.
- **대안**: Gradle 멀티모듈, 완전 MSA(여러 부트 앱).
- **선택**: 단일 앱 + 도메인별 패키지(`order`, `product`, `backoffice`, `common`). Kafka는 토픽으로 논리 분리.
- **이유**: 데모의 목적은 "기술 포인트 실증"이지 운영 가능한 MSA가 아니다. 단일 앱이면 실행·부하측정·디버깅이 단순하고, Kafka 비동기/캐시/RBAC/Batch 4축을 모두 한 프로세스에서 보여줄 수 있다. 프로젝트 원칙 "범위를 넓히지 말 것"과 일치.
- **트레이드오프**: 진짜 서비스 경계(네트워크 분리, 독립 배포)는 보여주지 못함. → 면접에선 "왜 데모는 모놀리식으로 단순화했고, 실제 MSA였다면 무엇이 달라지는가"를 설명하는 방식으로 보완.

## 5. 주문 도메인 최소 모델 + 동기 버전 우선 (축 1 — 1단계)

- **맥락**: 축 1의 최종 목표는 동기 vs Kafka 비동기 비교 측정. 비교가 성립하려면 기준선(동기)이 먼저 필요.
- **결정**: `Order(productId, quantity, status, createdAt)`만으로 시작. 상품 도메인과 FK 없이 `productId`만 보관. `POST /api/orders`는 저장 후 즉시 응답.
- **이유**: (1) 비교 측정에 필요한 건 "주문 접수 경로의 처리량"이지 도메인 완성도가 아님. (2) 가격·재고·회원은 4축 어디에도 필수가 아니라 범위 폭발 요인. (3) 상태 enum(CREATED/COMPLETED/FAILED)은 비동기 버전의 컨슈머 확정·DLQ 흐름을 미리 고려한 것.
- **트레이드오프**: 실제 이커머스 주문(금액 계산, 재고 차감)과 거리가 있음 → 면접에선 "측정 대상 경로만 남기고 단순화했다"로 설명.
- **보안**: Spring Security가 클래스패스에 있어 기본 전체 잠금 → 임시 `SecurityConfig`로 `/api/**`, `/actuator/**` permitAll. 축 3에서 JWT + RBAC로 교체 예정.

## 6. 부하테스트: k6 + 오픈 모델(constant-arrival-rate)

- **맥락**: 프로젝트 원칙은 "k6 (또는 JMeter)". TPS 목표 측정이 핵심.
- **선택**: k6, 그리고 도착률 고정의 **오픈 모델** 실행기.
- **이유 (k6)**: JS 코드로 시나리오 작성 → 스크립트가 git에 남아 측정 재현 가능. 단일 바이너리(Go)라 부하기 자체 오버헤드 작음. JMeter GUI/XML 대비 리뷰·버전관리 용이.
- **이유 (오픈 모델)**: closed 모델(VU 고정)은 서버가 느려지면 요청 발생도 같이 느려져 수치가 낙관됨(coordinated omission). "초당 1000건이 들어올 때 버티는가"를 물으려면 도착률을 서버 상태와 무관하게 유지해야 함.
- **트레이드오프**: 오픈 모델은 VU를 동적으로 늘리므로 부하기 자원 소모가 큼 → maxVUs 상한 설정. 부하기·앱 동일 머신이라는 한계는 benchmarks.md에 명시.

## 7. 비동기 주문 접수 경로: Kafka 발행 후 즉시 202 (축 1 — 2단계)

- **맥락**: 동기 버전은 요청 경로에 DB INSERT가 있다(측정 1-a: 1000/s에서 p95 435~626ms). 비동기 버전의 가설은 "요청 경로에서 DB를 빼면 응답시간이 준다".
- **결정**: `POST /api/orders/async` → orderKey(UUID) 발급 → `order.created` 토픽 발행 → **브로커 ack을 기다리지 않고** 202 + orderKey 반환. DB 저장은 컨슈머가 수행.
- **대안**:
  - (a) `send().get()`으로 브로커 ack 후 응답 — 유실 없지만 요청 경로에 네트워크 왕복이 들어가 비동기 이점 감소.
  - (b) Transactional Outbox — 로컬 DB에 이벤트를 같이 저장 후 별도 릴레이가 발행. 유실 없음. 단, 요청 경로에 DB INSERT가 다시 들어가므로 이 데모의 비교 목적(DB 없는 접수 경로)과 충돌.
- **선택 이유**: 측정 목적이 "접수 경로 최소화 시 응답시간/TPS"이므로 가장 가벼운 fire-and-forget을 기준으로 측정. 프로듀서 기본값이 acks=all + enable.idempotence=true(Kafka 3.x)라 **브로커에 닿기만 하면** 중복·유실 없이 기록됨. 위험 구간은 "202 응답 후 ~ 브로커 도달 전" 앱 크래시/브로커 다운뿐이며, 콜백 로그로 감지.
- **트레이드오프**: 202를 받고도 주문이 유실될 수 있는 좁은 창이 존재. 운영이면 (b) Outbox로 보완할 지점 — 면접에서 이 트레이드오프를 설명하는 것 자체가 목적.
- **orderKey를 서버가 발급하는 이유**: DB ID는 컨슈머가 INSERT하기 전엔 없음 → 클라이언트에게 즉시 돌려줄 조회 키가 필요. UUID는 충돌 걱정 없이 무상태로 발급 가능하고, Kafka 파티션 키 + 멱등성 키를 겸한다.

## 8. 컨슈머 멱등성: 존재 확인(1차) + DB 유니크 제약(2차), orderKey = 파티션 키

- **맥락**: Kafka는 at-least-once — 오프셋 커밋 전 리밸런스/재시작이면 같은 이벤트가 재전달된다. 중복 소비 시 주문이 2건 생기면 안 됨.
- **대안**:
  - (a) Redis SETNX로 처리 마킹 — 빠르지만 Redis 장애 시 멱등성 자체가 깨짐. 마킹과 DB 저장이 원자적이지 않아 마킹 후 저장 실패하면 유실.
  - (b) DB 유니크 제약만 — 확실하지만 중복마다 예외 발생 → 예외가 흐름 제어 수단이 됨.
  - (c) Kafka 트랜잭션(EOS) — 컨슈머→프로듀서 체인용. DB 쓰기엔 적용 안 됨.
- **선택**: `existsByOrderKey` 사전 검사(일반 경로) + `order_key` 유니크 제약(백스톱)의 2중 방어.
- **이유**: orderKey를 **파티션 키**로 쓰므로 같은 주문의 중복 이벤트는 항상 같은 파티션 → 같은 컨슈머 스레드에서 **순차** 처리. 따라서 검사-삽입 사이 경합은 사실상 리밸런스 직후의 좁은 창뿐이고, 그 경우만 유니크 제약이 잡는다. 제약 위반 → 에러 핸들러 재시도 → 존재 확인에 걸려 정상 스킵(자기 치유, DLQ 미오염). 멱등성의 최종 근거가 DB 제약이므로 인프라 추가 의존(Redis) 없이 저장소 하나로 닫힌다.
- **트레이드오프**: 이벤트마다 SELECT 1회 추가 (컨슈머 경로라 클라이언트 응답시간엔 영향 없음, 처리량 영향은 측정으로 확인).

## 9. 재시도 + DLQ: 1초 고정 백오프 × 2회 재시도 후 order.created.dlq

- **맥락**: 컨슈머 처리 실패(알림 실패, DB 일시 장애 등) 시 무한 재소비(poison pill)로 파티션이 막히면 안 됨.
- **결정**: `DefaultErrorHandler(FixedBackOff(1000ms, 2))` — 총 3회 시도 후 `DeadLetterPublishingRecoverer`로 `order.created.dlq` 발행. 역직렬화 실패는 `ErrorHandlingDeserializer`로 잡아 같은 경로로 보냄.
- **대안**:
  - (a) 지수 백오프(ExponentialBackOff) — 장애가 길 때 브로커/DB 압박을 줄이지만, **블로킹 재시도라 백오프 동안 해당 파티션 소비가 멈춤**. 긴 백오프 = 정상 메시지 지연.
  - (b) 비블로킹 재시도(@RetryableTopic, retry 토픽 체인) — 파티션이 안 막히지만 토픽 수가 늘고 **순서 보장이 깨짐**(같은 orderKey의 후속 이벤트가 먼저 처리될 수 있음). 멱등성 설계가 파티션 내 순차 처리에 기대고 있어 충돌.
  - (c) 재시도 없이 즉시 DLQ — 일시 장애(네트워크 순단)도 전부 DLQ로 가서 수동 개입 비용 증가.
- **선택 이유**: 짧은 고정 백오프는 일시 장애만 흡수하고 파티션 정체를 최소화. 순서 보장(멱등성 전제)을 지키려면 블로킹 재시도여야 함. DLQ를 `<topic>.DLT` 기본 규칙 대신 `order.created.dlq`로 명시 — DLQ는 1파티션이라 원본 파티션 번호(0~2)를 그대로 쓸 수 없어 파티션 선택은 프로듀서에 위임(-1).
- **트레이드오프**: DLQ 메시지의 재처리(수동 재발행) 도구는 미구현 — 데모 범위 밖. 면접 포인트: "DLQ에 쌓인 뒤 어떻게 하나"에 대한 답(헤더에 원본 토픽/예외 기록됨 → 원인 수정 후 재발행).

## 10. 배치 컨슈머 전환: 이벤트당 비용을 배치로 상각 (측정 1-c)

- **맥락**: 레코드 단위 컨슈머가 ~195건/s. 동시성 스케일(3→12스레드)은 2.4×에 그치고 접수 경로 p95를 열화시킴(측정 1-c-i). 병목은 이벤트당 고정 비용 — SELECT + INSERT + 트랜잭션 커밋(redo log fsync) + Docker 프록시 왕복 3회.
- **결정**: `@KafkaListener(batch=true)` — 폴링 배치(최대 500건)당 기처리 필터 SELECT 1회(IN) + multi-row `INSERT IGNORE` 1회 + 커밋 1회. 결과 ≥2000건/s (10배+, 측정 1-c-ii).
- **세부 선택과 이유**:
  - **JdbcTemplate 직접 사용**: IDENTITY 전략에선 Hibernate가 INSERT JDBC 배칭을 비활성화함(채번 위해 즉시 실행 필요). MySQL엔 시퀀스가 없어 ID 전략 변경 비용이 더 큼 → 컨슈머 저장 경로만 JDBC로.
  - **INSERT IGNORE**: 유니크(order_key) 충돌 = 기처리 주문 → 조용히 스킵. 멱등 2차 방어를 한 문장에 흡수. FK 없는 테이블이라 IGNORE가 삼킬 다른 제약 위반이 사실상 없음. `ON DUPLICATE KEY UPDATE` 대안은 Connector/J가 배치 재작성(rewriteBatchedStatements)을 못 하는 케이스가 있어 배제.
  - **알림 실패 시 부분 완결 + `BatchListenerFailedException(index)`**: 에러 핸들러는 index 앞 레코드의 오프셋을 커밋하므로, **던지기 전에 앞 레코드들을 먼저 저장**해야 유실이 없다. 이후 index부터 재전달 → 재시도/DLQ는 실패 레코드만 (9번 정책 유지).
- **트레이드오프**:
  - 배치 INSERT 자체가 실패(DB 순단)하면 배치 전체 재시도 → 이미 발송된 알림이 재발송될 수 있는 창 존재. 알림이 멱등하지 않다면 발송 이력 테이블이 필요한 지점 — 데모에선 로그라 수용.
  - 리스너 단위 지연이 약간 증가(배치 채우는 시간) — 처리 완료까지 1초 미만이라 무시 가능.
- **교훈(면접 포인트)**: 처리량 문제에서 스레드를 늘리기 전에 **단위 작업의 I/O 횟수**를 먼저 줄여라. 동시성 4배(2.4×)보다 배치화(10×+)가 압도적이었다.

## 11. 통합 테스트 컨텍스트 단일화 (IntegrationTestBase)

- **맥락**: `@MockitoSpyBean` 유무로 테스트 클래스마다 Spring 컨텍스트가 갈렸고, 캐시에 살아있는 여러 컨텍스트의 Kafka 컨슈머가 **같은 그룹으로 경쟁 소비** → 다른 컨텍스트가 이벤트를 가져간 테스트가 간헐 실패 (파티션 12 증설 후 표면화).
- **결정**: 모든 통합 테스트가 `IntegrationTestBase`(동일 어노테이션 + spy 선언)를 상속해 단일 컨텍스트 공유. 컨텍스트 1개 = 컨슈머 그룹 멤버 1세트 = 결정적 소비.
- **부수 효과**: 컨텍스트 기동 1회로 테스트 스위트가 빨라짐.

## 12. 상품 조회 캐시: look-aside 2계층 + 커밋 후 delete 무효화 (축 2)

- **맥락**: 상품 조회는 읽기 편중(읽기 ≫ 쓰기) 워크로드의 대표. 이력서의 "Caffeine L1 → Redis L2 → MySQL 계층화 + 변경 시 무효화"를 실증한다. 캐싱 값은 엔티티가 아닌 `ProductResponse` DTO — 영속성 컨텍스트 밖에서 안전하고 직렬화 형태가 API 응답과 동일.

- **읽기 경로: 수동 look-aside (L1 미스 → L2 → DB → 역방향 적재)**
  - **대안**: Spring Cache 추상화(`@Cacheable` + 커스텀 2계층 CacheManager) — 코드는 짧지만 계층 전이·single-flight·부분 무효화가 추상화 뒤에 숨는다.
  - **선택 이유**: 이 프로젝트의 목적이 "계층 동작을 이해하고 설명"이므로 L1→L2→DB 전이가 코드에 그대로 드러나는 명시적 구현(`ProductCacheLayer`)을 택했다. 캐시 히트 시 트랜잭션·DB 커넥션을 아예 타지 않는 것도 코드로 확인된다.
  - **트레이드오프**: 다른 도메인에 재사용하려면 일반화 필요. 도메인 1개(상품)뿐이라 수용.

- **무효화: invalidate-on-write — 새 값 set이 아니라 delete**
  - **대안**: write-through(쓰기 시 캐시에 새 값 set) — 다음 조회가 미스를 안 내지만, 동시 쓰기 2건의 set 순서가 역전되면 **옛값이 최종 잔류**한다(write-write race). delete는 최악이 "미스 1회 추가"라 실패 모드가 안전한 쪽으로 닫힌다.
  - **순서: DB 커밋 → L2 delete → pub/sub publish.** `TransactionTemplate`으로 커밋 시점을 코드에 드러냈다. `@Transactional` 메서드 안에서 evict하면 커밋 전에 다른 스레드가 옛값을 읽어 재적재한다.
  - **잔여 race**: evict 직전(커밋 전)에 DB를 읽은 스레드가 evict 후에 캐시에 put하면 옛값이 남을 수 있다. 정석 해법(버전 비교 put, 지연 이중 삭제)은 데모 범위 밖 — **TTL이 불일치 상한**(L1 60초, L2 10분)이라는 것을 명시하고 수용.

- **L1/L2 정합성: Redis pub/sub로 전 인스턴스 L1 evict + L1 TTL 백스톱**
  - L2(Redis)는 공유라 delete 한 번이면 끝. 문제는 **프로세스 내 L1** — 멀티 인스턴스에서 다른 인스턴스의 L1은 원격에서 직접 못 지운다.
  - **대안**: (a) L1에 짧은 TTL만 — 단순하지만 TTL 동안 인스턴스 간 불일치 방치. (b) Redis keyspace notifications — 키 이벤트를 구독하지만 설정 의존(`notify-keyspace-events`)이고 의미가 "키 삭제됨"뿐. (c) 명시적 무효화 채널 pub/sub.
  - **선택**: (c) `cache:invalidate:product` 채널. 쓴 인스턴스도 채널 왕복을 기다리지 않고 로컬 L1은 즉시 제거.
  - **한계**: pub/sub는 at-most-once — 구독 끊김/유실 시 그 인스턴스 L1엔 옛값이 남는다. → **L1 TTL 60초가 유실 시 불일치 상한**. (Kafka로 무효화 이벤트를 보내면 유실은 없지만 무효화 하나에 토픽·컨슈머 추가는 과함.)

- **Cache Stampede 대응**
  - **인스턴스 내**: Caffeine `get(key, loader)`가 같은 키의 동시 미스를 키 단위로 직렬화 — DB 로드는 1회만 실행(single-flight). 통합 테스트로 검증(동시 20조회 → `findById` 1회).
  - **인스턴스 간**: 미적용 — 중복 로드 상한이 "인스턴스 수"라 폭주가 아니다. 대안(분산락 SETNX, PER(확률적 조기 재계산), logical TTL)은 비용 대비 이득이 데모에선 없음 — 면접에서 트레이드오프로 설명.
  - **동시 만료 분산**: L2 TTL에 0~60초 jitter — 핫키들이 같은 순간 일제히 만료되어 DB로 몰리는 것을 분산.

- **장애 격리**: L2 읽기/쓰기 실패(Redis 다운)는 캐시 미스로 강등하고 DB로 폴백 — 캐시 계층 장애가 조회 실패로 전파되지 않는다. 단, evict의 L2 delete가 실패하면 L2에 옛값이 TTL까지 잔류할 수 있음(로그로 감지).

## 13. 백오피스 RBAC: JWT(HS256) + 역할 enum 단일 컬럼 (축 3 — 1단계)
- **권한 모델: `User.role` enum(USER/ADMIN) 단일 컬럼**
  - **대안**: Role/Permission 정규화 테이블(user_roles, role_permissions) — 역할·권한이 런타임에 늘어나는 시스템의 정석이지만, 이 데모는 역할 2개·보호 자원 1종(`/api/admin/**`)뿐이라 조인 3개가 순수 오버헤드.
  - **확장 지점**: 권한이 리소스 단위로 세분화되면 테이블 분리 + 메서드 보안(`@PreAuthorize`)으로 전환.
- **인증: JWT(jjwt, HS256 대칭키), stateless**
  - **대안**: 세션 + Redis — 서버 측 강제 무효화가 되지만 요청마다 세션 저장소 조회가 필요. JWT는 stateless라 고부하(1000 TPS) 환경과 결이 맞고, 이력서의 JWT 경험 실증 목적과 일치.
  - **트레이드오프**: 발급된 토큰은 강제 무효화 불가 → 만료 1시간으로 피해 상한을 둠. 역할을 클레임에 내장 → 인가 시 DB 조회 0회, 대신 역할 변경이 토큰 만료까지 미반영.
  - 단일 서버라 대칭키(HS256)로 충분. 발급자/검증자가 분리되면 RS256(공개키 검증)으로 갈 지점.
- **URL 보안 vs 메서드 보안: URL 패턴 한 곳(SecurityConfig)**
  - 보호 자원이 `/api/admin/**` 하나뿐이라 설정 한 곳에 모아 전체 보호 범위가 한눈에 보이게 했다.
- **보호 범위: 부하테스트 대상(주문·상품)은 permitAll 유지**
  - 인증 필터를 끼우면 축 1·2에서 측정한 수치의 전제(매 요청 JWT 파싱 비용 없음)가 바뀐다. 백오피스 경로만 보호.
- **ADMIN 생성 경로: 가입 API는 USER 고정, ADMIN은 부팅 시드(AdminAccountInitializer)**
  - 가입 요청에서 역할을 받으면 권한 상승 구멍이 된다. 시드 비밀번호는 데모라 yml 평문 — 운영이면 환경변수/시크릿 주입.
- **401/403 분리**: 미인증은 401(entry point), 인증됐지만 권한 부족은 403(access denied handler)으로 명시 — 기본 설정은 둘 다 403으로 뭉개질 수 있다. 필터는 무효 토큰에서 응답을 끊지 않고 미인증으로 통과시켜 판정 책임을 인가 단계 한곳에 모은다.

## 14. 월별 정산 배치: DB 집계 + clear→aggregate 2스텝 (축 3 — 2단계)
- **잡 구조: clearStep(해당 월 정산 삭제) → aggregateStep(청크 집계 적재)**
  - 같은 달 재실행 = 덮어쓰기라 잡 전체가 멱등. JobParameters에 `requestedAt`(타임스탬프)을 넣어 같은 달도 매번 새 JobInstance로 실행 가능하게 했다 — Spring Batch는 동일 파라미터의 COMPLETED 잡 재실행을 막기 때문.
  - **대안**: upsert(ON DUPLICATE KEY) — 삭제 스텝이 없어지지만, 이번 달 집계에서 사라진 상품의 잔존 행을 못 지운다. delete-then-insert가 결과를 항상 "이번 실행의 산출물"로 닫아준다.
- **집계 위치: DB(GROUP BY)에서 — 리더가 "상품별 합계" 행을 받는다**
  - **대안**: 주문 행을 그대로 읽어 프로세서에서 합산 — 주문 수백만 행이 전부 애플리케이션을 통과하고, 합산 상태를 스텝 재시작 간 유지해야 하는 문제가 생긴다. GROUP BY로 리더 입력을 "상품 수" 규모로 줄이면 청크 모델과 자연스럽게 맞는다.
  - 리더는 `JdbcPagingItemReader`(sort key = product_id) — 커서 리더와 달리 페이지 단위 독립 쿼리라 청크 트랜잭션과 궁합이 좋고 재시작 안전.
- **청크 크기 100 / 트랜잭션 경계 = 청크**
  - 청크당 1 트랜잭션(읽기 100행 → 가공 → 쓰기 100행 커밋). 실패 시 해당 청크만 롤백.
  - 입력 행 수가 "상품 수"라 수백~수천 규모 — 100이면 트랜잭션이 충분히 짧고, 더 키워서 얻을 게 없다. 주문 행 직접 처리(수십만+)였다면 측정으로 조정할 값.
- **정산 대상: status ≠ FAILED (CREATED 포함)**
  - 동기 주문은 CREATED로 머물고(후속 처리 개념이 없음), COMPLETED는 비동기 컨슈머가 찍는다. 두 경로 모두 유효한 매출이므로 FAILED만 제외.
- **단가 스냅샷**: Settlement에 상품명·금액을 박제 — 정산 후 가격이 바뀌어도 과거 정산이 흔들리지 않게. 주문 시점 가격이 아니라 정산 시점 가격인 것은 Order가 가격을 안 들고 있는 현 모델의 한계(데모 수용, 운영이면 주문에 단가 스냅샷).
- **상품이 삭제된 주문**: 프로세서가 null 반환으로 스킵 — FK 없는 느슨한 결합(5번 결정)의 트레이드오프를 정산에서 흡수.
- **트리거: ADMIN 전용 API + 동기 실행(기본 JobLauncher)**
  - 데모는 정산이 초 단위라 동기 응답으로 결과를 바로 확인. 분 단위로 길어지면 비동기 런처 + 실행 ID 폴링으로 전환할 지점. 스케줄 실행(@Scheduled)은 데모 범위 밖.

## 15. 1000 TPS 튜닝: 풀 크기는 측정이 정당화한 것만 — 전부 기본값/기존값 유지 (축 4)
- **Tomcat `threads.max`: 기본 200 유지**
  - 측정 3에서 100/200/400을 같은 절차(새 JVM + orders TRUNCATE + 워밍업)로 비교 — p95가 전부 런 간 편차 밴드(1.4~2.4s) 안에 겹쳐 **스레드 수는 결정 변수가 아님**. in-flight(≈1,000)가 어떤 풀 크기도 초과하는 상황이라, 병목은 워커 수가 아니라 부하 시 요청당 서비스 시간 증가(커밋 fsync + 동일 머신 경합).
  - 원칙: 수치가 정당화하지 않는 튜닝 값을 설정 파일에 박지 않는다. 박는 순간 "왜 400인가"에 답할 근거가 없는 마법 숫자가 된다.
- **HikariCP `maximum-pool-size`: 20 유지**
  - 측정 1-a에서 1000/s 부하 중 active/pending 연속 샘플링 결과 전부 0 — 커넥션 풀은 한 번도 병목인 적이 없다. INSERT가 sub-ms라 풀 회전이 충분히 빠름.
- **Kafka 파티션: 12 유지 (1-c에서 증설한 값)**
  - 파티션 수 자체는 처리율에 영향 없음을 1-c-i에서 확인(3→12 동일 ~195건/s). 처리율을 바꾼 건 배치화(1-c-ii)였고, 배치 컨슈머는 concurrency 3으로 1000건/s 이상을 실시간 추종(측정 4 드레인 ≤2초). 12는 향후 concurrency 증설 여지로만 의미.
- **종합 결론 (면접 한 줄)**: 이 시스템에서 1000 TPS를 만든 결정 변수는 풀 튜닝이 아니라 **요청 경로에서 DB를 제거한 설계**(주문 = Kafka 비동기 접수, 조회 = L1 캐시)였다. 같은 머신에서 동기 단일 경로는 ~900/s에서 초 단위 큐잉(측정 3), 혼합 경로(조회 80 + 주문 20)는 3000/s까지 p95 한 자릿수 ms(측정 4).
- **한계 명시**: 부하기·앱·DB가 같은 머신 — 절대값은 보수적으로, 비교는 같은 세션 안에서만. 일 단위 환경 편차가 튜닝 효과보다 컸다(측정 3).

## 16. 모니터링: Prometheus pull + Grafana 프로비저닝 코드화 (선택 과제)
- **수집: Micrometer → `/actuator/prometheus`를 Prometheus가 5초 간격 pull**
  - **대안**: push 방식(StatsD, CloudWatch) — pull은 스크레이프 성공 여부로 타깃 생사가 같이 관측되고, 로컬 데모에 표준적. 앱은 호스트에서 돌므로 컨테이너의 Prometheus가 `host.docker.internal`로 접근.
  - 스크레이프 5초: 부하 런이 30초 단위라 기본 15초로는 런 하나에 점이 2개뿐.
- **Grafana 설정은 클릭이 아니라 코드(provisioning)로**: 데이터소스·대시보드를 yml/json으로 저장소에 둠 — 컨테이너를 지워도 `docker compose up`만으로 같은 화면이 재현된다. 포트폴리오는 "다시 띄우면 그대로 나온다"가 중요.
- **`percentiles-histogram` 트레이드오프**: 서버측 p95/p99를 PromQL(`histogram_quantile`)로 계산하려면 버킷 노출이 필요(uri당 ~70 시계열). 단일 앱 데모 규모라 수용. **k6(클라이언트측) p95와 서버측 p95의 차이 = 서블릿 밖 큐잉** — 측정 1-a에서 수동으로 했던 병목 위치 분석이 대시보드로 상시화된다.
- **대시보드 패널 선정 기준**: 부하테스트 중 봐야 하는 것만 — 처리량(uri별), p95/p99, 5xx 에러율, Hikari active/pending(풀 포화 신호), Kafka 리스너 처리율(컨슈머 랙 추세), JVM 힙. 예쁜 그래프 나열이 아니라 측정 1~4에서 실제로 확인했던 지표들.
- **측정 원칙과의 관계**: 1-a 3차에서 측정 중 메트릭 폴링이 수치를 흔든 교훈이 있다 — benchmarks.md의 기존 수치는 모니터링 없이 측정한 값이므로, 이후 비교 측정 시 모니터링 가동 여부를 동일하게 맞출 것.

## 17. [msa 브랜치] MSA 1단계: Gradle 멀티모듈 — 패키지 경계를 모듈 경계로 승격

- **맥락**: 2번 결정(모듈러 모놀리식)의 후속. main은 측정 수치와 코드의 일치성을 위해 모놀리스로 보존하고, MSA 전환은 이 브랜치에서 단계적으로 진행한다. 1단계는 배포 형태(단일 부트 앱)와 동작을 바꾸지 않으면서 도메인 경계만 빌드 수준에서 강제한다.
- **모듈 구성**: `product` / `order` / `backoffice`(→product) / `app`(부트스트랩: @SpringBootApplication + application.yml + 통합 테스트).
  - 통합 테스트는 전 도메인을 한 컨텍스트로 띄우므로(11번, IntegrationTestBase) 도메인 모듈이 아니라 app에 둔다.
- **common 패키지 해체**: common/config에 있던 3개 설정이 사실 전부 특정 도메인 소유였다 — CacheConfig→product(ProductCacheLayer 배선), KafkaConfig→order(주문 토픽·DLQ 정책), SecurityConfig→backoffice(JWT 필터 배선). "공통"이라는 이름이 숨기고 있던 결합이 모듈화로 드러난 것 자체가 수확.
- **남은 도메인 간 결합 1개를 빌드 파일에 명시**: `backoffice → product` (정산 프로세서의 상품 단가 조회, 14번). MSA 2단계에서 API 호출 또는 이벤트 기반 데이터 복제로 해소할 지점.
- **컴파일 설정 명시화 (전환 중 발견)**:
  - `-parameters`: 단일 모듈에선 부트 플러그인이 자동 주입했지만 java-library 모듈엔 없어 @PathVariable 이름 해석이 깨졌다(테스트 7개 실패로 발견). 루트에서 전 모듈에 명시.
  - `UTF-8` 소스 인코딩: Windows 기본(CP949) 의존이 컴파일 에러로 표면화 — 루트에서 고정.
- **부수 정리**: 미사용 `spring-boot-starter-cache` 제거(@EnableCaching/CacheManager 미사용 — 캐시는 12번대로 수동 look-aside). 모듈별 의존성 명세가 정확해지는 것이 멀티모듈의 부수 이득.
- **검증**: 전 모듈 컴파일 + 통합 테스트 25개 전체 통과 (docker compose 인프라 기동 상태).
- **트레이드오프**: 빌드 파일 5개로 증가, 모듈 간 의존을 명시해야 하는 비용. 대신 경계 위반이 컴파일 에러로 잡힌다.

## 18. [msa 브랜치] MSA 2단계: 정산→상품 의존을 이벤트 기반 데이터 복제로 해소

- **맥락**: 17번에서 명시해 둔 유일한 도메인 간 결합 — 정산 프로세서가 `ProductRepository`를 직접 조회. MSA로 가면 이건 "다른 서비스의 DB를 직접 읽는" 안티패턴이 된다.
- **대안**:
  - (a) 동기 API 호출 — 정산 배치가 상품마다 product API를 호출. 배치 특성상 N+1 원격 호출이 되고, 정산 실행 가능 여부가 product 서비스 가용성에 묶인다(배치가 야간에 돌 때 product가 점검 중이면 정산 불가).
  - (b) 공유 계약 모듈(port 인터페이스) — 컴파일 의존은 끊기지만 런타임 결합(호출)은 그대로. 3단계에서 어차피 (a)의 문제로 돌아온다.
  - (c) **이벤트 기반 데이터 복제** — product가 `product.changed`를 발행, backoffice가 로컬 `product_replica` 테이블을 유지, 정산은 로컬만 읽는다.
- **선택**: (c). 대량 읽기가 필요한 배치는 동기 호출이 아니라 로컬 복제본 조인이 정석이고, 이 프로젝트의 정체성(이벤트 드리븐)과 기존 Kafka 인프라에 자연스럽게 얹힌다. 정산 실행이 product 가용성과 완전히 분리된다.
- **구현 포인트**:
  - **발행**: 상품 생성·수정 시 **커밋 후** 발행 (캐시 evict와 같은 원칙 — 커밋 전 발행이면 롤백된 상품이 복제됨). 생성도 TransactionTemplate으로 전환해 커밋 시점을 코드에 드러냈다. fire-and-forget + 콜백 로그 — 주문 발행(7번)과 같은 트레이드오프, 운영이면 outbox.
  - **계약 = JSON 스키마, 클래스 공유 없음**: 컨슈머(backoffice)는 product의 이벤트 클래스를 import하지 않고 자기 표현(`ProductChangedMessage`)으로 파싱한다. 상수(토픽 이름)도 공유하지 않는다 — 클래스·상수 공유도 컴파일 의존이고, 그걸 없애는 게 이 단계의 목적. 전역 컨슈머 설정이 주문 타입에 묶여 있어 전용 리스너 팩토리(String 역직렬화)를 둔다.
  - **순서·멱등**: 키 = productId → 같은 상품은 같은 파티션에서 순차. 복제본 PK = 원본 ID의 upsert라 at-least-once 재전달에 멱등.
  - **실패 처리**: 별도 DLQ 없음 — 복제본은 다음 변경 이벤트가 자기 치유하는 데이터라 주문(9번)처럼 건별 보존이 불필요. 기본 에러 핸들러(재시도 후 스킵)로 충분.
- **트레이드오프**:
  - **최종 일관성**: 이벤트 지연·유실 구간만큼 복제본이 원본과 어긋날 수 있다. 정산은 월 단위 배치라 초 단위 복제 지연은 무의미 — 이 워크로드가 (c)에 유리한 이유.
  - **초기 적재(backfill) 미구현**: 복제본은 이벤트로만 채워지므로, 이 변경 이전에 존재하던 상품은 다음 수정 전까지 복제본에 없어 정산에서 스킵된다. 운영이면 1회 초기 적재 마이그레이션이 필요한 지점 — 데모에선 명시하고 수용. (테스트도 이 제약 때문에 상품을 리포지토리 직접 저장이 아니라 API로 생성하도록 수정.)
  - 같은 DB 안에 사실상 같은 데이터가 두 벌(products, product_replica) — 단일 DB인 지금은 낭비처럼 보이지만, 3단계에서 DB가 분리되면 이 테이블이 그대로 backoffice 서비스의 로컬 데이터가 된다.
- **검증**: 통합 테스트 25개 전체 통과. 정산 테스트가 "API 생성 → 복제 대기(awaitility) → 정산 실행" 흐름으로 복제 경로 자체를 검증한다.

## 19. [msa 브랜치] MSA 3a단계: 서비스별 부트 앱 분리 — 조합 앱은 테스트 하네스로 유지

- **맥락**: 17·18번으로 모듈 경계와 컴파일 의존은 정리됨. 이제 실행 단위를 분리한다. 전체 그림과 남은 과제는 docs/msa-architecture.md.
- **결정**: 도메인 모듈은 그대로 두고 **부트스트랩 모듈 3개 추가** — product-app(:8081) / order-app(:8082) / backoffice-app(:8083). 각 앱의 클래스패스에 자기 도메인 모듈만 올려, 루트 패키지 스캔이 곧 서비스 경계가 된다(스캔 필터 불필요).
- **조합 앱(app, :8080) 유지**: 통합 테스트 25개가 전 도메인 단일 컨텍스트(11번)를 전제하므로 테스트 하네스로 남긴다. 서비스 간 흐름의 검증은 분리 앱 3개를 띄운 수동 E2E로 보완 — 운영이면 컨트랙트 테스트/컴포즈 기반 E2E로 자동화할 지점.
- **3a의 의도된 한계 — DB·인프라는 아직 공유**:
  - DB 분리(3b)의 선행 조건이 따로 있다: **정산 리더가 orders 테이블을 직접 SQL 집계하는 데이터 결합** — 단일 DB라 보이지 않던 두 번째 숨은 결합(첫 번째는 18번의 product). 해소 방안 비교는 msa-architecture.md(월별 집계 API가 유력 — 상품 복제와 반대 선택인 이유는 호출 패턴 차이).
  - 인증은 분리 후에도 HS256 유지 — 발급자=검증자(backoffice)라 성립. RS256은 다른 서비스가 토큰을 검증할 때.
- **검증 (수동 E2E, 3개 서비스 동시 기동)**: 상품 생성(8081) → 비동기 주문 202+컨슈머 저장(8082) → 무토큰 정산 401 → 로그인·정산 실행(8083) → 정산 행의 상품명·금액이 정확. 마지막 항목이 핵심 — backoffice-service는 products 테이블을 읽지 않으므로, **정산 행이 맞다 = 서비스 간 이벤트 복제가 동작한다**는 증명.
- **트레이드오프**: 같은 코드가 두 실행 형태(조합/분리)를 가져 yml이 4벌 — 설정 드리프트 위험. 데모에선 주석으로 기준(app/)을 명시, 운영이면 공통 설정 추출이나 중앙 설정으로 갈 지점.

## 20. [msa 브랜치] MSA 3b-1단계: 정산→orders 직접 SQL을 order-service 월별 집계 API로 전환

- **맥락**: 19번에서 발견한 두 번째 숨은 결합 — 정산 리더가 `FROM orders` SQL로 order 도메인 테이블을 직접 GROUP BY. DB 분리(3b-2)의 선행 조건.
- **대안 비교** (msa-architecture.md): (a) 동기 집계 API / (b) 주문 이벤트 복제 / (c) CDC.
- **선택: (a) 동기 집계 API** — 18번(상품 복제)과 **반대** 선택. 이유는 호출 패턴: 상품은 정산 행마다 조회(N+1 위험)라 복제가 맞고, 주문은 **월 1회 페이지 단위 집계**라 동기 호출 비용이 무시 가능하다. (b)는 동기 주문이 이벤트를 발행하지 않아 발행 지점 추가가 필요한 데다 주문 전 건 복제는 볼륨 부담. 같은 문제처럼 보여도 워크로드가 답을 가른다.
- **구현 포인트**:
  - **order-service**: `GET /internal/orders/monthly-sales?month=&page=&size=` — GROUP BY는 데이터 소유자가 DB에서 수행, FAILED 제외 정책(14번)도 소유자가 강제. product_id 정렬 고정으로 페이지 간 중복·누락 없는 안정 페이징. `/internal` 네임스페이스로 비공개 API임을 표시(데모는 공개, 운영이면 내부망/서비스 간 인증).
  - **backoffice**: `MonthlyOrderSalesReader`(ItemReader)가 RestClient로 페이지 단위 호출. 응답은 backoffice 소유 `ProductSales`로 역직렬화 — 18번과 같은 "클래스 공유 없는 JSON 계약".
  - **재시작 안전성 트레이드오프**: JdbcPagingItemReader와 달리 ExecutionContext 미저장 — 정산 잡은 clear 스텝 덕에 처음부터 재실행이 멱등(14번)이라 중간 재개가 불필요.
  - **테스트 하네스 변화**: 조합 앱 통합 테스트가 MOCK 환경에선 HTTP 자기 호출이 불가 → `RANDOM_PORT`로 전환하고 order-service URL을 런타임 포트로 치환. MockMvc는 RANDOM_PORT에서도 동작해 기존 테스트 25개 무수정 통과.
- **새 트레이드오프**: 정산 실행이 order-service 가용성에 결합된다(월 배치라 재시도로 흡수 가능). Tomcat 기본 응답이 페이지 크기 100 × 상품 수 규모라 페이로드 부담 없음.
- **검증**: 통합 테스트 25개 통과 + 분리 앱 3개 E2E — backoffice-app(8083)의 정산이 order-app(8082) 집계 API를 **프로세스 간 HTTP로 호출**해 정확한 정산 행 생성(수량·금액 일치). 백오피스 코드에서 타 도메인 테이블 접근이 0이 되어 3b-2(스키마 분리)가 가능해졌다.

## 21. [msa 브랜치] MSA 3b-2단계: 서비스별 DB 스키마 분리 + 컨슈머 그룹 분리

- **결정**: `tps1000` 단일 스키마 → 서비스 소유 스키마 3개(`tps_product`/`tps_order`/`tps_backoffice`). 같은 MySQL 인스턴스(로컬 데모 한계 — 운영이면 인스턴스도 분리). 조합 하네스(app)와 main(모놀리스)은 tps1000을 그대로 사용 — 측정 수치·테스트 전제 불변.
- **초기화**: docker-entrypoint-initdb.d 스크립트(새 볼륨 자동) + 기존 볼륨용 1회 수동 docker exec(스크립트 상단에 명령 기록).
- **테이블 소유 검증**: products→tps_product / orders→tps_order / users·settlements·product_replica·BATCH_* 메타→tps_backoffice. 크로스 스키마 SQL이 물리적으로 불가능한 상태에서 E2E 정산 성공 = 18번(복제)·20번(집계 API) 설계의 최종 증명.
- **복제본 재구축 = 토픽 재생**: 새 스키마의 빈 product_replica를 마이그레이션 없이 **새 컨슈머 그룹 + auto-offset-reset=earliest**로 채웠다(27행 재생). 토픽 보존 기간이 곧 재구축 가능 기간.
- **작업 중 발견한 결함 — 컨슈머 그룹은 배포 단위(DB)마다 분리해야 한다**:
  - 1차: 하네스(테스트)와 backoffice-app이 복제 그룹을 공유 → 먼저 뜬 하네스가 재생을 가져가 복제본이 하네스 DB(tps1000)에 쌓이고 분리 DB는 비었다(경쟁 소비). → 그룹 이름을 프로퍼티로 분리(`backoffice.replica-consumer-group`).
  - 2차: 주문 그룹(tps1000)도 하네스와 order-app이 공유 — 동시에 뜨면 주문이 두 DB로 쪼개지고, 분리 앱을 강제 종료한 직후엔 좀비 멤버가 세션 타임아웃(45초)까지 파티션을 붙들어 테스트가 간헐 실패(실제 재현). → order-app 그룹을 `order-service`로 분리.
  - 교훈: Kafka 컨슈머 그룹의 단위는 "같은 코드"가 아니라 **"같은 데이터 저장소를 채우는 배포 단위"**다.
- **과거 데이터 이관**: 비동기 주문은 새 그룹의 토픽 재생으로 tps_order에 적재(멱등 INSERT IGNORE). 동기 주문·기존 상품 등 이벤트 없는 데이터의 이관(mysqldump)은 데모 범위 밖으로 명시.
- **검증**: 통합 테스트 25개 통과(하네스 전제 불변) + 분리 앱 3개 E2E — 상품·주문·정산이 각자 스키마에만 기록되고 정산 수치 정확(수량 4 × 900 = 3,600).

## 22. [msa 브랜치] MSA 3c단계: API 게이트웨이 — 전환 단계 완료

- **결정**: `gateway-app`(:8080, Spring Cloud Gateway) — 클라이언트 단일 진입점. 모놀리스와 같은 포트라 **클라이언트 인터페이스가 전환 전후 동일**하다(조합 앱과 동시 기동만 불가).
- **대안**: nginx(컨테이너) — 현실적이지만 라우팅이 인프라 설정으로 빠진다. Spring Cloud Gateway는 이 포트폴리오의 스택과 일관되고 라우팅 규칙이 코드 리뷰 대상이 된다.
- **라우트를 yml이 아닌 Java DSL로**: Spring Cloud는 버전에 따라 라우트 프로퍼티 prefix가 바뀌어 왔다(`spring.cloud.gateway.routes` → `...server.webflux.routes`). `RouteLocatorBuilder` API는 안정적. 서비스 주소만 프로퍼티로 분리.
- **버전 선택의 함정 (기록 가치)**: BOM 버전을 존재하지 않는 2025.0.4로 잘못 지정하자 **모듈의 전체 dependencyManagement가 무너져 모든 의존성이 버전 없음으로 실패**했다 — BOM 임포트 실패는 해당 의존성만이 아니라 판 전체를 깨뜨린다. Maven Central 메타데이터로 실존 버전(2025.0.2, Boot 3.5 호환 트레인 — 2025.1.x는 Boot 4용)을 확인하고 해결.
- **`/internal/**` 비라우팅**: 서비스 간 내부 API(주문 집계)는 게이트웨이에서 404 — 외부 진입점에서 내부 계약이 차단된다. 단 로컬 데모는 서비스 포트(8081~8083)가 호스트에 직접 열려 있어 우회 가능 — 운영이면 서비스를 내부망에만 바인딩할 지점.
- **게이트웨이는 토큰을 검증하지 않는다**: 인가 책임을 backoffice 한곳에 유지(13번의 401/403 분리 설계 그대로 경유 동작 확인). RS256 전환은 게이트웨이/타 서비스가 검증 주체가 될 때 — 현 구조에선 불필요 판단으로 종료.
- **검증 (전 트래픽을 :8080으로만)**: 상품 생성 → 비동기 주문 → 컨슈머 저장 → 무토큰 401 → 로그인 → 정산 실행·수치 정확(5 × 1,200 = 6,000) → `/internal` 404. 4개 앱 동시 기동.
- **남은 것(범위 밖 명시)**: 게이트웨이 경유 부하 측정(별도 베이스라인), 서비스별 Prometheus 타깃 확장, 분산 추적. — **이로써 msa-architecture.md의 전환 단계(1→3c)는 완료.**

## 23. [msa 브랜치] 보안 하드닝 1차: 시크릿 외부화 + 내부 API 서비스 간 인증

- **맥락**: 전환 단계(17~22번) 완료 후 보안 점검에서 나온 두 가지 — (1) JWT 키·DB/관리자 비밀번호가 yml·compose에 평문 커밋, (2) `/internal/**`가 게이트웨이 비라우팅(22번)뿐이라 호스트에 열린 서비스 포트(8081~8083)로 우회 호출 가능. 측정 조건(부하테스트 경로의 무인증)을 건드리지 않는 항목만 1차로 작업.
- **시크릿 외부화**: 모든 민감 값을 `${ENV_VAR:로컬기본값}`으로 전환 (JWT_SECRET, DB_USERNAME/DB_PASSWORD, BACKOFFICE_ADMIN_PASSWORD, INTERNAL_API_TOKEN + compose의 MySQL/Grafana). 로컬 기본값을 남긴 이유: 데모는 clone 직후 실행이 가능해야 하고, 테스트(25개)가 별도 설정 없이 돌아야 한다. 운영 배포라면 기본값을 제거하고 비밀관리자(Vault/Secrets Manager)에서 주입할 지점. `.env.example` 커밋, `.env`는 gitignore. **한계 명시**: 과거 커밋 히스토리에 기존 값이 남아 있다 — 공개 저장소에서 이 값이 운영 가치가 없는 데모 값이라 수용, 실서비스였다면 키 로테이션이 필수.
- **내부 API 인증 — 공유 시크릿 헤더**:
  - **대안**: (a) 내부망 바인딩 — 로컬 단일 호스트 데모에선 표현 불가. (b) mTLS — 인증서 발급/배포 인프라가 데모 범위를 넘는다. (c) **`X-Internal-Token` 공유 시크릿** — 호출자가 정산 리더 하나뿐인 현 구조에 비용 대비 적정. 운영이면 (a)+(b)로 올라갈 지점.
  - **검증 지점은 order 모듈의 서블릿 필터**(InternalApiTokenFilter): spring-security 의존이 없는 order-app에서도 동작해야 해서 security 체인이 아니라 독립 필터로. 조합 앱에선 security(permitAll 통과) 뒤에서 같은 필터가 검증한다.
  - **상수 시간 비교**(MessageDigest.isEqual): equals는 불일치 위치에 따라 비교 시간이 달라져 타이밍 공격 여지 — 비용이 0이라 데모에서도 정석대로.
  - **헤더 이름은 문자열로만 공유**: order/backoffice 간 상수 클래스를 공유하지 않는다 — 18번(클래스 공유 없는 JSON 계약)과 같은 원칙.
- **측정 조건 불변**: `/api/orders/**`·`/api/products/**` 무인증 유지(13번 근거 그대로) — 부하테스트 수치·통합 테스트 전제에 영향 없음. 정산 경로만 헤더 한 개 추가(월 1회 호출이라 성능 무관).
- **남은 하드닝(범위 밖 명시)**: 로그인 rate limiting(게이트웨이 + Redis), actuator 관리 포트 분리, 주문 조회 소유자 검증, Flyway 전환.
- **검증**: 통합 테스트 전체 통과(정산 테스트가 토큰 포함 호출 경로를 검증) + 무토큰/오토큰 `/internal` 호출 401 확인.

## 24. [msa 브랜치] 보안 하드닝 2차: 게이트웨이 로그인 rate limiting + 미존재 조회 404 수정

- **로그인 rate limiting — 게이트웨이 IP별 토큰 버킷**:
  - **맥락**: 23번에서 범위 밖으로 미뤄둔 항목. `/api/auth/login`에 횟수 제한이 없어 admin 계정 무한 브루트포스가 가능했다(BCrypt ~100ms가 유일한 감속).
  - **위치 선택 — 게이트웨이 vs backoffice**: 게이트웨이(Spring Cloud Gateway `RequestRateLimiter` + `RedisRateLimiter`)를 택했다. (1) 이미 떠 있는 Redis를 카운터 저장소로 재활용, (2) 카운터가 Redis에 있어 게이트웨이를 수평 확장해도 한도가 하나로 유지, (3) 차단된 요청이 backoffice에 도달하기 전에 끊겨 BCrypt 연산 비용도 막는다. 트레이드오프: 서비스 포트(8083) 직접 호출은 게이트웨이를 안 거친다 — `/internal`과 같은 로컬 데모 한계(운영이면 내부망 바인딩, 22·23번과 동일 지점).
  - **인증 라우트만 분리**: `/api/auth/**` 전용 라우트에만 필터 — 부하테스트 대상 경로(order·product)에 걸면 측정 조건이 바뀐다(13번 원칙 유지).
  - **키 = 직접 연결 IP**: X-Forwarded-For는 클라이언트가 위조 가능해 쓰지 않는다. 단일 게이트웨이 구조라 직접 주소가 곧 클라이언트. 운영에서 LB 뒤에 서면 신뢰할 수 있는 홉 수만큼만 XFF를 파싱할 지점.
  - **수치 (replenish 2/s, burst 5)**: 정상 사용자는 로그인 1~2회면 충분, 자동화 공격은 초당 2회로 묶인다. 초과는 429 + `X-RateLimit-*` 헤더. Redis 장애 시 fail-open(통과) — 로그인 가용성을 카운터 인프라에 묶지 않는 선택.
  - **한계 명시**: IP 기준이라 분산(botnet) 공격은 못 막는다 — 계정 기준 잠금/지연은 backoffice 도메인 로직으로 올라갈 지점(범위 밖).
- **미존재 조회 500 → 404 수정**: 23번 검증 중 발견 — `EntityNotFoundException` 핸들러가 없어 미존재 주문/상품 조회가 500으로 새고 있었다. 클라이언트가 "없음"과 "서버 장애"를 구분 못 하고, ID 스캔이 서버 에러로 기록돼 모니터링 노이즈가 된다. `@RestControllerAdvice`로 404(ProblemDetail) 변환 — 어드바이스는 모듈별(order·product, 17번 경계 원칙), 조합 앱에선 공존하지만 같은 매핑이라 무해.
- **검증**: 통합 테스트 전체 통과 + 4개 앱 E2E — 게이트웨이 경유 미존재 주문/상품 404(ProblemDetail 본문), 오인증 로그인 연타 10회에 401×5(버스트 소진) 후 429 발생, 충전 속도(2/s)만큼 간헐 통과 — 토큰 버킷 정상 동작.

## 25. [msa 브랜치] 보안 하드닝 3차: actuator 관리 포트 분리 + Flyway 전환 + IDOR 문서화

- **actuator 관리 포트 분리** (`management.server.port`):
  - **맥락**: 23번에서 미룬 항목 — metrics·prometheus까지 서비스 포트에 `permitAll`로 노출돼 엔드포인트별 응답시간·JVM 상태가 외부에 보였다.
  - **결정**: 서비스 포트와 분리 — app·gateway 9080 / product 9081 / order 9082 / backoffice 9083 (조합 앱과 게이트웨이는 서비스 포트처럼 동시 기동이 없어 9080 공유). Prometheus 타깃을 9080으로 변경. 운영이면 관리 포트만 내부망에 열어 노출 끝점이 사라진다.
  - **확인된 동작**: 서비스 포트의 /actuator는 product·order·gateway에서 404, backoffice에선 security 기본 거부(anyRequest)에 걸려 401 — 어느 쪽이든 비접근. `/actuator/**` permitAll은 관리 포트 응답을 위해 유지.
- **Flyway 전환** (`ddl-auto: update` → `validate`):
  - **맥락**: ddl-auto: update는 엔티티 변경이 곧바로 운영 DDL이 되는 구조 — 의도치 않은 스키마 변경(컬럼 타입 변경, 제약 누락)이 배포와 동시에 조용히 적용된다. 17번부터 줄곧 "운영이면 전환할 지점"으로 적어온 항목.
  - **DDL 기준**: Hibernate가 만들어 둔 실제 스키마(`SHOW CREATE TABLE`)를 그대로 고정 — 손으로 옮겨 적다 어긋나면 validate가 부팅을 막아주는 구조라, 어긋남이 침묵하지 않는다.
  - **버전 번호를 모듈별로 분할 (V1 product / V2 order / V3 backoffice)**: 마이그레이션 파일을 (앱이 아니라) 도메인 모듈의 `db/migration`에 둬서 DDL의 단일 출처를 유지한다. 조합 앱은 세 모듈을 한 클래스패스에서 모두 보므로 버전이 겹치면 Flyway가 실패 — 모듈별 번호 분할이 그 충돌을 피하면서 분리 앱(자기 버전만 보임)과 조합 앱(V1~V3 전부) 양쪽에서 성립한다.
  - **기존 DB 호환**: `baseline-on-migrate: true` + 마이그레이션 전체 `IF NOT EXISTS` — 기존 볼륨(테이블 존재)은 baseline 후 no-op, 새 볼륨은 정상 적용. 검증 결과 tps1000은 baseline+V2·V3, 서비스 스키마는 각자 자기 버전만 기록됐다.
  - **BATCH_* 메타는 제외**: Spring Batch 자체 초기화가 버전별 공식 DDL을 관리 — 중복 정의하면 배치 업그레이드 때 두 출처가 어긋난다.
- **IDOR 문서화** (`GET /api/orders/{orderId}`): 순차 ID라 타인 주문 열람 가능. 이 경로는 무인증 측정 대상(13번)이라 "소유자" 개념 자체가 성립하지 않아 데모 범위에서 수용 — 실서비스라면 인증 주체의 소유 검증 + 외부 키는 추측 불가 값(비동기 주문 orderKey가 이미 그 패턴). 코드 주석으로 한계를 명시(OrderController).
- **검증**: 통합 테스트 전체 통과(validate 부팅 = 마이그레이션 DDL과 엔티티 일치 증명) + 4개 앱 E2E — 관리 포트 4개 health 200, 서비스 포트 /actuator 비접근, Prometheus 새 타깃(9080) up, 로그인·404·내부 토큰 스모크 정상. — **이로써 23번에서 적어둔 남은 하드닝 항목은 모두 처리(분산 공격 대응·내부망 격리는 운영 영역으로 명시).**

## 26. [msa 브랜치] 게이트웨이 경유 부하 측정 — 같은 세션 A/B 비교 설계

- **맥락**: 22번에서 범위 밖으로 미룬 "게이트웨이 경유 부하 측정(별도 베이스라인)". 측정 수치는 benchmarks.md 측정 5.
- **핵심 설계 — 측정 4와 비교하지 않는다**: 측정 3에서 "일 단위 환경 편차가 튜닝 효과보다 크다"를 확인했으므로, 다른 날짜의 측정 4와 비교하는 대신 **같은 세션에서 조합 앱(A, 모놀리스 형태) → 게이트웨이+분리 앱 4개(B)를 연달아 측정**했다. 이 설계 덕에 "게이트웨이 홉 + 프로세스 분리 비용"이 날짜 편차와 분리된다 — 측정 방법론이 누적 교훈 위에 서는 구조.
- **결과 한 줄**: 1000~2000 TPS 평시 영역에서 홉 비용 ≈ 1ms(런 간 편차와 같은 자릿수, B 2차 런 p95 2.8~3.3ms·에러 0)이고, 한계 구간(5000/s)에선 B가 뚜렷이 먼저 무너진다(에러 12% vs 1.4%) — 단일 머신에 JVM 5개가 동거하는 자원 경합이 원인 후보, 분해는 머신 분리가 필요해 범위 밖.
- **절차에서 얻은 교훈 — 워밍업은 구성 단수에 비례**: B의 2000/s 1차가 에러 5.6%로 무너졌는데 직후 3000/s와 2000/s 2차는 에러 0% — 용량이 아니라 다단 커넥션 풀(k6→게이트웨이→백엔드)·JIT 워밍업 부족이었다. 1차/2차를 모두 기록해 편차 자체를 데이터로 남겼다(측정 1-a의 콜드 스타트 기록과 같은 원칙).
- **부수 확인**: 보안 하드닝(23~25) 적용 상태로 측정 — Flyway validate·내부 API 토큰·관리 포트 분리가 부하 경로에 영향 없음을 겸사 확인. 정합성은 매 런 COUNT 증가분 = 202 응답 수 일치(한계 구간 포함 무손실), 세션 누적 147,984 = DISTINCT = COMPLETED. 부팅 시 토픽 재생 백로그 66,568건 ~13초 소진 — 21번의 "재구축 = 토픽 재생"이 부하 규모에서도 성립.
- **남은 것(범위 밖)**: 부하기·서비스 머신 분리(한계 원인 분해), 서비스별 Prometheus 타깃 확장.
