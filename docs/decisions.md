## 0. 이 프로젝트가 실증하려는 이력서 경험

이력서의 다음 경험을 **직접 구현하고 측정**해서 면접에서 설명 가능하게 만드는 것이 목표다.

| 이력서 항목 | 출처(이력서) | 이 프로젝트의 실증 축 |
|---|---|---|
| Kafka 비동기 주문 처리, DLQ + 재시도, 1000 TPS 대응, 응답시간 50% 단축 | 폐쇄몰 주문 시스템(2024.05~12) | **축 1. 주문 처리** — 동기 vs Kafka 비동기 비교 측정 |
| 캐시 계층화 (CDN → Redis L2 → Caffeine L1 → MySQL), 변경 시 무효화 | 폐쇄몰 주문 시스템 캐시 플로우 | **축 2. 상품 조회 캐시 계층화** |
| Spring Batch 월별 정산, Spring Security RBAC, 특정 IP 접근 제어 | 백오피스 Java 마이그레이션(2024.12~2025.03) | **축 3. 백오피스 (RBAC + Batch)** |
| 1000 TPS 감당 웹사이트 운영 | Skills 요약 | **축 4. 부하테스트 (k6, 1000 TPS 목표)** |

핵심: 이력서엔 "성과 수치"(매출 300%, 다운타임 80% 감소 등)만 적혀 있고 **재현 가능한 측정 근거가 없다**.
이 프로젝트는 그 수치를 **내 손으로 재현·측정**해서, 면접에서 "어떻게 측정했고 병목이 무엇이었나"까지 말할 수 있게 한다.

## 1. 빌드 도구: Gradle (Groovy DSL)

- **맥락**: 빈 폴더에서 시작, 빌드 도구 미정.
- **대안**: Maven(pom.xml), Gradle Kotlin DSL.
- **선택**: Gradle Groovy DSL.
- **이유**: Spring Boot 포트폴리오에서 가장 일반적, 빌드 속도·설정 간결, wrapper로 별도 설치 불필요(팀/면접관 재현 용이). Groovy 예제가 Kotlin DSL보다 풍부.
- **트레이드오프**: Kotlin DSL 대비 타입 안정성·IDE 자동완성이 약함. 데모 규모에선 영향 작음.

## 2. 아키텍처: 모듈러 모놀리식 (단일 Spring Boot 앱)

- **맥락**: 이력서엔 Payment / Order / Notification 이 **별도 서비스(MSA)**로 기술됨.
- **대안**: Gradle 멀티모듈, 완전 MSA(여러 부트 앱).
- **선택**: 단일 앱 + 도메인별 패키지(`order`, `product`, `backoffice`, `common`). Kafka는 토픽으로 논리 분리.
- **이유**: 데모의 목적은 "기술 포인트 실증"이지 운영 가능한 MSA가 아니다. 단일 앱이면 실행·부하측정·디버깅이 단순하고, Kafka 비동기/캐시/RBAC/Batch 4축을 모두 한 프로세스에서 보여줄 수 있다. 프로젝트 원칙 "범위를 넓히지 말 것"과 일치.
- **트레이드오프**: 진짜 서비스 경계(네트워크 분리, 독립 배포)는 보여주지 못함. → 면접에선 "왜 데모는 모놀리식으로 단순화했고, 실제 MSA였다면 무엇이 달라지는가"를 설명하는 방식으로 보완.

  - **대안**: Zookeeper 동반 구성, Confluent 이미지.
  - **선택**: KRaft 단일 노드(apache/kafka 공식 이미지).
  - **이유**: Zookeeper 제거로 컨테이너 1개로 Kafka 운영 → 데모 환경 단순화. 공식 이미지가 KRaft 스토리지 자동 포맷 지원.
  - **트레이드오프**: 단일 브로커라 복제·고가용성은 시연 불가(replication-factor=1). 데모 목적상 수용.

## 5. 주문 도메인 최소 모델 + 동기 버전 우선 (축 1 — 1단계)

- **맥락**: 축 1의 최종 목표는 동기 vs Kafka 비동기 비교 측정. 비교가 성립하려면 기준선(동기)이 먼저 필요.
- **결정**: `Order(productId, quantity, status, createdAt)`만으로 시작. 상품 도메인과 FK 없이 `productId`만 보관. `POST /api/orders`는 저장 후 즉시 응답.
- **이유**: (1) 비교 측정에 필요한 건 "주문 접수 경로의 처리량"이지 도메인 완성도가 아님. (2) 가격·재고·회원은 4축 어디에도 필수가 아니라 범위 폭발 요인. (3) 상태 enum(CREATED/COMPLETED/FAILED)은 비동기 버전의 컨슈머 확정·DLQ 흐름을 미리 고려한 것.
- **트레이드오프**: 실제 이커머스 주문(금액 계산, 재고 차감)과 거리가 있음 → 면접에선 "측정 대상 경로만 남기고 단순화했다"로 설명.
- **보안**: Spring Security가 클래스패스에 있어 기본 전체 잠금 → 임시 `SecurityConfig`로 `/api/**`, `/actuator/**` permitAll. 축 3에서 JWT + RBAC로 교체 예정.

## 6. 부하테스트: k6 + 오픈 모델(constant-arrival-rate)

- **맥락**: 프로젝트 원칙은 "k6 (또는 JMeter)". TPS 목표 측정이 핵심.
- **선택**: k6, 그리고 도착률 고정의 **오픈 모델** 실행기.
- **이유 (k6)**: JS 코드로 시나리오 작성 → 스크립트가 git에 남아 측정 재현 가능. 단일 바이너리(Go)라 부하기 자체 오버헤드 작음. JMeter GUI/XML 대비 리뷰·버전관리 용이.
- **이유 (오픈 모델)**: closed 모델(VU 고정)은 서버가 느려지면 요청 발생도 같이 느려져 수치가 낙관됨(coordinated omission). "초당 1000건이 들어올 때 버티는가"를 물으려면 도착률을 서버 상태와 무관하게 유지해야 함.
- **트레이드오프**: 오픈 모델은 VU를 동적으로 늘리므로 부하기 자원 소모가 큼 → maxVUs 상한 설정. 부하기·앱 동일 머신이라는 한계는 benchmarks.md에 명시.

## 7. 비동기 주문 접수 경로: Kafka 발행 후 즉시 202 (축 1 — 2단계)

- **맥락**: 동기 버전은 요청 경로에 DB INSERT가 있다(측정 1-a: 1000/s에서 p95 435~626ms). 비동기 버전의 가설은 "요청 경로에서 DB를 빼면 응답시간이 준다".
- **결정**: `POST /api/orders/async` → orderKey(UUID) 발급 → `order.created` 토픽 발행 → **브로커 ack을 기다리지 않고** 202 + orderKey 반환. DB 저장은 컨슈머가 수행.
- **대안**:
  - (a) `send().get()`으로 브로커 ack 후 응답 — 유실 없지만 요청 경로에 네트워크 왕복이 들어가 비동기 이점 감소.
  - (b) Transactional Outbox — 로컬 DB에 이벤트를 같이 저장 후 별도 릴레이가 발행. 유실 없음. 단, 요청 경로에 DB INSERT가 다시 들어가므로 이 데모의 비교 목적(DB 없는 접수 경로)과 충돌.
- **선택 이유**: 측정 목적이 "접수 경로 최소화 시 응답시간/TPS"이므로 가장 가벼운 fire-and-forget을 기준으로 측정. 프로듀서 기본값이 acks=all + enable.idempotence=true(Kafka 3.x)라 **브로커에 닿기만 하면** 중복·유실 없이 기록됨. 위험 구간은 "202 응답 후 ~ 브로커 도달 전" 앱 크래시/브로커 다운뿐이며, 콜백 로그로 감지.
- **트레이드오프**: 202를 받고도 주문이 유실될 수 있는 좁은 창이 존재. 운영이면 (b) Outbox로 보완할 지점 — 면접에서 이 트레이드오프를 설명하는 것 자체가 목적.
- **orderKey를 서버가 발급하는 이유**: DB ID는 컨슈머가 INSERT하기 전엔 없음 → 클라이언트에게 즉시 돌려줄 조회 키가 필요. UUID는 충돌 걱정 없이 무상태로 발급 가능하고, Kafka 파티션 키 + 멱등성 키를 겸한다.

## 8. 컨슈머 멱등성: 존재 확인(1차) + DB 유니크 제약(2차), orderKey = 파티션 키

- **맥락**: Kafka는 at-least-once — 오프셋 커밋 전 리밸런스/재시작이면 같은 이벤트가 재전달된다. 중복 소비 시 주문이 2건 생기면 안 됨.
- **대안**:
  - (a) Redis SETNX로 처리 마킹 — 빠르지만 Redis 장애 시 멱등성 자체가 깨짐. 마킹과 DB 저장이 원자적이지 않아 마킹 후 저장 실패하면 유실.
  - (b) DB 유니크 제약만 — 확실하지만 중복마다 예외 발생 → 예외가 흐름 제어 수단이 됨.
  - (c) Kafka 트랜잭션(EOS) — 컨슈머→프로듀서 체인용. DB 쓰기엔 적용 안 됨.
- **선택**: `existsByOrderKey` 사전 검사(일반 경로) + `order_key` 유니크 제약(백스톱)의 2중 방어.
- **이유**: orderKey를 **파티션 키**로 쓰므로 같은 주문의 중복 이벤트는 항상 같은 파티션 → 같은 컨슈머 스레드에서 **순차** 처리. 따라서 검사-삽입 사이 경합은 사실상 리밸런스 직후의 좁은 창뿐이고, 그 경우만 유니크 제약이 잡는다. 제약 위반 → 에러 핸들러 재시도 → 존재 확인에 걸려 정상 스킵(자기 치유, DLQ 미오염). 멱등성의 최종 근거가 DB 제약이므로 인프라 추가 의존(Redis) 없이 저장소 하나로 닫힌다.
- **트레이드오프**: 이벤트마다 SELECT 1회 추가 (컨슈머 경로라 클라이언트 응답시간엔 영향 없음, 처리량 영향은 측정으로 확인).

## 9. 재시도 + DLQ: 1초 고정 백오프 × 2회 재시도 후 order.created.dlq

- **맥락**: 컨슈머 처리 실패(알림 실패, DB 일시 장애 등) 시 무한 재소비(poison pill)로 파티션이 막히면 안 됨.
- **결정**: `DefaultErrorHandler(FixedBackOff(1000ms, 2))` — 총 3회 시도 후 `DeadLetterPublishingRecoverer`로 `order.created.dlq` 발행. 역직렬화 실패는 `ErrorHandlingDeserializer`로 잡아 같은 경로로 보냄.
- **대안**:
  - (a) 지수 백오프(ExponentialBackOff) — 장애가 길 때 브로커/DB 압박을 줄이지만, **블로킹 재시도라 백오프 동안 해당 파티션 소비가 멈춤**. 긴 백오프 = 정상 메시지 지연.
  - (b) 비블로킹 재시도(@RetryableTopic, retry 토픽 체인) — 파티션이 안 막히지만 토픽 수가 늘고 **순서 보장이 깨짐**(같은 orderKey의 후속 이벤트가 먼저 처리될 수 있음). 멱등성 설계가 파티션 내 순차 처리에 기대고 있어 충돌.
  - (c) 재시도 없이 즉시 DLQ — 일시 장애(네트워크 순단)도 전부 DLQ로 가서 수동 개입 비용 증가.
- **선택 이유**: 짧은 고정 백오프는 일시 장애만 흡수하고 파티션 정체를 최소화. 순서 보장(멱등성 전제)을 지키려면 블로킹 재시도여야 함. DLQ를 `<topic>.DLT` 기본 규칙 대신 `order.created.dlq`로 명시 — DLQ는 1파티션이라 원본 파티션 번호(0~2)를 그대로 쓸 수 없어 파티션 선택은 프로듀서에 위임(-1).
- **트레이드오프**: DLQ 메시지의 재처리(수동 재발행) 도구는 미구현 — 데모 범위 밖. 면접 포인트: "DLQ에 쌓인 뒤 어떻게 하나"에 대한 답(헤더에 원본 토픽/예외 기록됨 → 원인 수정 후 재발행).

## 10. 배치 컨슈머 전환: 이벤트당 비용을 배치로 상각 (측정 1-c)

- **맥락**: 레코드 단위 컨슈머가 ~195건/s. 동시성 스케일(3→12스레드)은 2.4×에 그치고 접수 경로 p95를 열화시킴(측정 1-c-i). 병목은 이벤트당 고정 비용 — SELECT + INSERT + 트랜잭션 커밋(redo log fsync) + Docker 프록시 왕복 3회.
- **결정**: `@KafkaListener(batch=true)` — 폴링 배치(최대 500건)당 기처리 필터 SELECT 1회(IN) + multi-row `INSERT IGNORE` 1회 + 커밋 1회. 결과 ≥2000건/s (10배+, 측정 1-c-ii).
- **세부 선택과 이유**:
  - **JdbcTemplate 직접 사용**: IDENTITY 전략에선 Hibernate가 INSERT JDBC 배칭을 비활성화함(채번 위해 즉시 실행 필요). MySQL엔 시퀀스가 없어 ID 전략 변경 비용이 더 큼 → 컨슈머 저장 경로만 JDBC로.
  - **INSERT IGNORE**: 유니크(order_key) 충돌 = 기처리 주문 → 조용히 스킵. 멱등 2차 방어를 한 문장에 흡수. FK 없는 테이블이라 IGNORE가 삼킬 다른 제약 위반이 사실상 없음. `ON DUPLICATE KEY UPDATE` 대안은 Connector/J가 배치 재작성(rewriteBatchedStatements)을 못 하는 케이스가 있어 배제.
  - **알림 실패 시 부분 완결 + `BatchListenerFailedException(index)`**: 에러 핸들러는 index 앞 레코드의 오프셋을 커밋하므로, **던지기 전에 앞 레코드들을 먼저 저장**해야 유실이 없다. 이후 index부터 재전달 → 재시도/DLQ는 실패 레코드만 (9번 정책 유지).
- **트레이드오프**:
  - 배치 INSERT 자체가 실패(DB 순단)하면 배치 전체 재시도 → 이미 발송된 알림이 재발송될 수 있는 창 존재. 알림이 멱등하지 않다면 발송 이력 테이블이 필요한 지점 — 데모에선 로그라 수용.
  - 리스너 단위 지연이 약간 증가(배치 채우는 시간) — 처리 완료까지 1초 미만이라 무시 가능.
- **교훈(면접 포인트)**: 처리량 문제에서 스레드를 늘리기 전에 **단위 작업의 I/O 횟수**를 먼저 줄여라. 동시성 4배(2.4×)보다 배치화(10×+)가 압도적이었다.

## 11. 통합 테스트 컨텍스트 단일화 (IntegrationTestBase)

- **맥락**: `@MockitoSpyBean` 유무로 테스트 클래스마다 Spring 컨텍스트가 갈렸고, 캐시에 살아있는 여러 컨텍스트의 Kafka 컨슈머가 **같은 그룹으로 경쟁 소비** → 다른 컨텍스트가 이벤트를 가져간 테스트가 간헐 실패 (파티션 12 증설 후 표면화).
- **결정**: 모든 통합 테스트가 `IntegrationTestBase`(동일 어노테이션 + spy 선언)를 상속해 단일 컨텍스트 공유. 컨텍스트 1개 = 컨슈머 그룹 멤버 1세트 = 결정적 소비.
- **부수 효과**: 컨텍스트 기동 1회로 테스트 스위트가 빨라짐.

## 12. 상품 조회 캐시: look-aside 2계층 + 커밋 후 delete 무효화 (축 2)

- **맥락**: 상품 조회는 읽기 편중(읽기 ≫ 쓰기) 워크로드의 대표. 이력서의 "Caffeine L1 → Redis L2 → MySQL 계층화 + 변경 시 무효화"를 실증한다. 캐싱 값은 엔티티가 아닌 `ProductResponse` DTO — 영속성 컨텍스트 밖에서 안전하고 직렬화 형태가 API 응답과 동일.

- **읽기 경로: 수동 look-aside (L1 미스 → L2 → DB → 역방향 적재)**
  - **대안**: Spring Cache 추상화(`@Cacheable` + 커스텀 2계층 CacheManager) — 코드는 짧지만 계층 전이·single-flight·부분 무효화가 추상화 뒤에 숨는다.
  - **선택 이유**: 이 프로젝트의 목적이 "계층 동작을 이해하고 설명"이므로 L1→L2→DB 전이가 코드에 그대로 드러나는 명시적 구현(`ProductCacheLayer`)을 택했다. 캐시 히트 시 트랜잭션·DB 커넥션을 아예 타지 않는 것도 코드로 확인된다.
  - **트레이드오프**: 다른 도메인에 재사용하려면 일반화 필요. 도메인 1개(상품)뿐이라 수용.

- **무효화: invalidate-on-write — 새 값 set이 아니라 delete**
  - **대안**: write-through(쓰기 시 캐시에 새 값 set) — 다음 조회가 미스를 안 내지만, 동시 쓰기 2건의 set 순서가 역전되면 **옛값이 최종 잔류**한다(write-write race). delete는 최악이 "미스 1회 추가"라 실패 모드가 안전한 쪽으로 닫힌다.
  - **순서: DB 커밋 → L2 delete → pub/sub publish.** `TransactionTemplate`으로 커밋 시점을 코드에 드러냈다. `@Transactional` 메서드 안에서 evict하면 커밋 전에 다른 스레드가 옛값을 읽어 재적재한다.
  - **잔여 race**: evict 직전(커밋 전)에 DB를 읽은 스레드가 evict 후에 캐시에 put하면 옛값이 남을 수 있다. 정석 해법(버전 비교 put, 지연 이중 삭제)은 데모 범위 밖 — **TTL이 불일치 상한**(L1 60초, L2 10분)이라는 것을 명시하고 수용.

- **L1/L2 정합성: Redis pub/sub로 전 인스턴스 L1 evict + L1 TTL 백스톱**
  - L2(Redis)는 공유라 delete 한 번이면 끝. 문제는 **프로세스 내 L1** — 멀티 인스턴스에서 다른 인스턴스의 L1은 원격에서 직접 못 지운다.
  - **대안**: (a) L1에 짧은 TTL만 — 단순하지만 TTL 동안 인스턴스 간 불일치 방치. (b) Redis keyspace notifications — 키 이벤트를 구독하지만 설정 의존(`notify-keyspace-events`)이고 의미가 "키 삭제됨"뿐. (c) 명시적 무효화 채널 pub/sub.
  - **선택**: (c) `cache:invalidate:product` 채널. 쓴 인스턴스도 채널 왕복을 기다리지 않고 로컬 L1은 즉시 제거.
  - **한계**: pub/sub는 at-most-once — 구독 끊김/유실 시 그 인스턴스 L1엔 옛값이 남는다. → **L1 TTL 60초가 유실 시 불일치 상한**. (Kafka로 무효화 이벤트를 보내면 유실은 없지만 무효화 하나에 토픽·컨슈머 추가는 과함.)

- **Cache Stampede 대응**
  - **인스턴스 내**: Caffeine `get(key, loader)`가 같은 키의 동시 미스를 키 단위로 직렬화 — DB 로드는 1회만 실행(single-flight). 통합 테스트로 검증(동시 20조회 → `findById` 1회).
  - **인스턴스 간**: 미적용 — 중복 로드 상한이 "인스턴스 수"라 폭주가 아니다. 대안(분산락 SETNX, PER(확률적 조기 재계산), logical TTL)은 비용 대비 이득이 데모에선 없음 — 면접에서 트레이드오프로 설명.
  - **동시 만료 분산**: L2 TTL에 0~60초 jitter — 핫키들이 같은 순간 일제히 만료되어 DB로 몰리는 것을 분산.

- **장애 격리**: L2 읽기/쓰기 실패(Redis 다운)는 캐시 미스로 강등하고 DB로 폴백 — 캐시 계층 장애가 조회 실패로 전파되지 않는다. 단, evict의 L2 delete가 실패하면 L2에 옛값이 TTL까지 잔류할 수 있음(로그로 감지).

## 13. 백오피스 RBAC: JWT(HS256) + 역할 enum 단일 컬럼 (축 3 — 1단계)
- **권한 모델: `User.role` enum(USER/ADMIN) 단일 컬럼**
  - **대안**: Role/Permission 정규화 테이블(user_roles, role_permissions) — 역할·권한이 런타임에 늘어나는 시스템의 정석이지만, 이 데모는 역할 2개·보호 자원 1종(`/api/admin/**`)뿐이라 조인 3개가 순수 오버헤드.
  - **확장 지점**: 권한이 리소스 단위로 세분화되면 테이블 분리 + 메서드 보안(`@PreAuthorize`)으로 전환.
- **인증: JWT(jjwt, HS256 대칭키), stateless**
  - **대안**: 세션 + Redis — 서버 측 강제 무효화가 되지만 요청마다 세션 저장소 조회가 필요. JWT는 stateless라 고부하(1000 TPS) 환경과 결이 맞고, 이력서의 JWT 경험 실증 목적과 일치.
  - **트레이드오프**: 발급된 토큰은 강제 무효화 불가 → 만료 1시간으로 피해 상한을 둠. 역할을 클레임에 내장 → 인가 시 DB 조회 0회, 대신 역할 변경이 토큰 만료까지 미반영.
  - 단일 서버라 대칭키(HS256)로 충분. 발급자/검증자가 분리되면 RS256(공개키 검증)으로 갈 지점.
- **URL 보안 vs 메서드 보안: URL 패턴 한 곳(SecurityConfig)**
  - 보호 자원이 `/api/admin/**` 하나뿐이라 설정 한 곳에 모아 전체 보호 범위가 한눈에 보이게 했다.
- **보호 범위: 부하테스트 대상(주문·상품)은 permitAll 유지**
  - 인증 필터를 끼우면 축 1·2에서 측정한 수치의 전제(매 요청 JWT 파싱 비용 없음)가 바뀐다. 백오피스 경로만 보호.
- **ADMIN 생성 경로: 가입 API는 USER 고정, ADMIN은 부팅 시드(AdminAccountInitializer)**
  - 가입 요청에서 역할을 받으면 권한 상승 구멍이 된다. 시드 비밀번호는 데모라 yml 평문 — 운영이면 환경변수/시크릿 주입.
- **401/403 분리**: 미인증은 401(entry point), 인증됐지만 권한 부족은 403(access denied handler)으로 명시 — 기본 설정은 둘 다 403으로 뭉개질 수 있다. 필터는 무효 토큰에서 응답을 끊지 않고 미인증으로 통과시켜 판정 책임을 인가 단계 한곳에 모은다.

## 14. 월별 정산 배치: DB 집계 + clear→aggregate 2스텝 (축 3 — 2단계)
- **잡 구조: clearStep(해당 월 정산 삭제) → aggregateStep(청크 집계 적재)**
  - 같은 달 재실행 = 덮어쓰기라 잡 전체가 멱등. JobParameters에 `requestedAt`(타임스탬프)을 넣어 같은 달도 매번 새 JobInstance로 실행 가능하게 했다 — Spring Batch는 동일 파라미터의 COMPLETED 잡 재실행을 막기 때문.
  - **대안**: upsert(ON DUPLICATE KEY) — 삭제 스텝이 없어지지만, 이번 달 집계에서 사라진 상품의 잔존 행을 못 지운다. delete-then-insert가 결과를 항상 "이번 실행의 산출물"로 닫아준다.
- **집계 위치: DB(GROUP BY)에서 — 리더가 "상품별 합계" 행을 받는다**
  - **대안**: 주문 행을 그대로 읽어 프로세서에서 합산 — 주문 수백만 행이 전부 애플리케이션을 통과하고, 합산 상태를 스텝 재시작 간 유지해야 하는 문제가 생긴다. GROUP BY로 리더 입력을 "상품 수" 규모로 줄이면 청크 모델과 자연스럽게 맞는다.
  - 리더는 `JdbcPagingItemReader`(sort key = product_id) — 커서 리더와 달리 페이지 단위 독립 쿼리라 청크 트랜잭션과 궁합이 좋고 재시작 안전.
- **청크 크기 100 / 트랜잭션 경계 = 청크**
  - 청크당 1 트랜잭션(읽기 100행 → 가공 → 쓰기 100행 커밋). 실패 시 해당 청크만 롤백.
  - 입력 행 수가 "상품 수"라 수백~수천 규모 — 100이면 트랜잭션이 충분히 짧고, 더 키워서 얻을 게 없다. 주문 행 직접 처리(수십만+)였다면 측정으로 조정할 값.
- **정산 대상: status ≠ FAILED (CREATED 포함)**
  - 동기 주문은 CREATED로 머물고(후속 처리 개념이 없음), COMPLETED는 비동기 컨슈머가 찍는다. 두 경로 모두 유효한 매출이므로 FAILED만 제외.
- **단가 스냅샷**: Settlement에 상품명·금액을 박제 — 정산 후 가격이 바뀌어도 과거 정산이 흔들리지 않게. 주문 시점 가격이 아니라 정산 시점 가격인 것은 Order가 가격을 안 들고 있는 현 모델의 한계(데모 수용, 운영이면 주문에 단가 스냅샷).
- **상품이 삭제된 주문**: 프로세서가 null 반환으로 스킵 — FK 없는 느슨한 결합(5번 결정)의 트레이드오프를 정산에서 흡수.
- **트리거: ADMIN 전용 API + 동기 실행(기본 JobLauncher)**
  - 데모는 정산이 초 단위라 동기 응답으로 결과를 바로 확인. 분 단위로 길어지면 비동기 런처 + 실행 ID 폴링으로 전환할 지점. 스케줄 실행(@Scheduled)은 데모 범위 밖.

## 15. 1000 TPS 튜닝: 풀 크기는 측정이 정당화한 것만 — 전부 기본값/기존값 유지 (축 4)
- **Tomcat `threads.max`: 기본 200 유지**
  - 측정 3에서 100/200/400을 같은 절차(새 JVM + orders TRUNCATE + 워밍업)로 비교 — p95가 전부 런 간 편차 밴드(1.4~2.4s) 안에 겹쳐 **스레드 수는 결정 변수가 아님**. in-flight(≈1,000)가 어떤 풀 크기도 초과하는 상황이라, 병목은 워커 수가 아니라 부하 시 요청당 서비스 시간 증가(커밋 fsync + 동일 머신 경합).
  - 원칙: 수치가 정당화하지 않는 튜닝 값을 설정 파일에 박지 않는다. 박는 순간 "왜 400인가"에 답할 근거가 없는 마법 숫자가 된다.
- **HikariCP `maximum-pool-size`: 20 유지**
  - 측정 1-a에서 1000/s 부하 중 active/pending 연속 샘플링 결과 전부 0 — 커넥션 풀은 한 번도 병목인 적이 없다. INSERT가 sub-ms라 풀 회전이 충분히 빠름.
- **Kafka 파티션: 12 유지 (1-c에서 증설한 값)**
  - 파티션 수 자체는 처리율에 영향 없음을 1-c-i에서 확인(3→12 동일 ~195건/s). 처리율을 바꾼 건 배치화(1-c-ii)였고, 배치 컨슈머는 concurrency 3으로 1000건/s 이상을 실시간 추종(측정 4 드레인 ≤2초). 12는 향후 concurrency 증설 여지로만 의미.
- **종합 결론 (면접 한 줄)**: 이 시스템에서 1000 TPS를 만든 결정 변수는 풀 튜닝이 아니라 **요청 경로에서 DB를 제거한 설계**(주문 = Kafka 비동기 접수, 조회 = L1 캐시)였다. 같은 머신에서 동기 단일 경로는 ~900/s에서 초 단위 큐잉(측정 3), 혼합 경로(조회 80 + 주문 20)는 3000/s까지 p95 한 자릿수 ms(측정 4).
- **한계 명시**: 부하기·앱·DB가 같은 머신 — 절대값은 보수적으로, 비교는 같은 세션 안에서만. 일 단위 환경 편차가 튜닝 효과보다 컸다(측정 3).
