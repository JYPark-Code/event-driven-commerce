## 30초 요약 (작동 방식을 물으면)

> "조회 80%/주문 20% 혼합 부하에서 1000 TPS를 에러 0%로 처리하는 커머스 데모입니다.
> 조회는 Caffeine(L1) → Redis(L2) → MySQL 캐시 계층으로 흡수해 p95를 541ms에서 577µs까지 줄였고,
> 주문은 Kafka에 적재 후 즉시 202를 반환하고 컨슈머가 배치 리스너 + JDBC batch로 저장해 처리량을 195건/s에서 2,000건/s 이상으로 올렸습니다.
> 정합성은 멱등 키 + DB 유니크 제약으로 전 측정 누적 중복 0건을 확인했습니다.
> 핵심 결론은 '1000 TPS를 만든 건 풀 튜닝이 아니라 요청 경로에서 DB를 제거한 설계'라는 것입니다."

마지막 문장이 이 프로젝트의 한 줄 결론 (결정 15).

## 축 1 — Kafka 비동기 주문

### Q. 202를 반환했는데 주문이 유실될 수 있지 않나요?
가능합니다. 브로커 ack을 기다리지 않는 fire-and-forget이라 "202 응답 후 ~ 브로커 도달 전" 앱 크래시/브로커 다운이라는 좁은 창이 존재합니다. 프로듀서 기본값이 acks=all + enable.idempotence=true라 **브로커에 닿기만 하면** 유실·중복이 없고, 위험 창은 콜백 로그로 감지합니다. 운영이라면 Transactional Outbox로 보완할 지점인데, 이 데모는 "접수 경로에서 DB를 뺐을 때의 응답시간"을 측정하는 게 목적이라 Outbox(요청 경로에 DB INSERT가 다시 들어감)와 충돌해 의도적으로 배제했습니다. (결정 7)

### Q. 같은 메시지가 두 번 소비되면요?
Kafka는 at-least-once라 재전달은 전제입니다. 방어는 2중입니다 — 1차: 배치 내 중복 제거 + `findExistingOrderKeys`(IN) 사전 필터, 2차: `order_key` 유니크 제약 + `INSERT IGNORE`. orderKey가 **파티션 키**라 같은 주문의 중복 이벤트는 항상 같은 파티션 = 같은 스레드에서 순차 처리되므로, 검사-삽입 사이 경합은 리밸런스 직후의 좁은 창뿐이고 그건 유니크 제약이 잡습니다. 멱등성의 최종 근거가 DB 제약이라 Redis 같은 추가 인프라 의존 없이 닫힙니다. (결정 8, `OrderEventConsumer.java`)

### Q. 컨슈머 처리량을 어떻게 10배 올렸나요?
병목은 이벤트당 고정 비용(SELECT + INSERT + 커밋 fsync + 네트워크 왕복 3회)이었습니다. 스레드를 3→12로 늘려봤지만 2.4×에 그쳤고(측정 1-c-i), 배치 리스너로 전환해 폴링 배치당 필터 SELECT 1회 + multi-row INSERT 1회 + 커밋 1회로 비용을 상각하니 195 → 2,000건/s 이상이 됐습니다(1-c-ii). **교훈: 처리량 문제에서 스레드를 늘리기 전에 단위 작업의 I/O 횟수부터 줄여라.** (결정 10)

### Q. 배치 처리 중간에 한 건이 실패하면 앞의 건들은요?
실패 레코드 **앞까지를 먼저 저장한 뒤** `BatchListenerFailedException(index)`를 던집니다. 에러 핸들러가 index 앞 레코드의 오프셋을 커밋하므로, 던지기 전에 저장하지 않으면 그 주문들은 영영 유실됩니다. 이후 index부터 재전달되어 재시도/DLQ는 실패 레코드만 적용됩니다. (결정 10, `OrderEventConsumer.java:50`)

### Q. poison pill로 파티션이 막히면요?
`FixedBackOff(1초 × 2회)` 후 `order.created.dlq`로 보냅니다. 지수 백오프는 블로킹 재시도 특성상 백오프 동안 파티션 소비가 멈춰 정상 메시지가 지연되고, 비블로킹 재시도(@RetryableTopic)는 순서 보장이 깨져 "파티션 내 순차"에 기대는 멱등성 설계와 충돌해 배제했습니다. (결정 9)

### Q. DLQ에 쌓인 메시지는 그다음 어떻게 하나요?
DLQ 메시지 헤더에 원본 토픽·파티션·예외가 기록되므로, 원인 수정 후 원본 토픽으로 재발행하는 게 운영 시나리오입니다. 재발행 도구 자체는 데모 범위 밖이라 미구현 — 이걸 먼저 인정하고 설계 방향을 말하는 게 안전합니다. (결정 9)

## 축 2 — 캐시 계층 (Caffeine L1 → Redis L2 → MySQL)

### Q. Redis가 죽으면 조회가 실패하나요?
아니요. L2 읽기/쓰기 실패는 캐시 미스로 강등하고 DB로 폴백합니다 — 캐시 계층 장애가 조회 실패로 전파되지 않게. 단 evict의 L2 delete가 실패하면 옛값이 L2 TTL(10분)까지 잔류할 수 있고, 이는 로그로 감지합니다. (결정 12, `ProductCacheLayer.java`)

### Q. cache stampede(핫키 동시 미스 폭주)는요?
인스턴스 내에서는 Caffeine `get(key, loader)`가 같은 키의 동시 미스를 키 단위로 직렬화해 DB 로드가 1회만 실행됩니다(single-flight, 동시 20조회 → `findById` 1회 통합 테스트로 검증). 인스턴스 간 중복 로드는 허용 — 상한이 "인스턴스 수"라 폭주가 아니고, 분산락/PER 같은 대안은 데모에선 비용 대비 이득이 없습니다. 동시 만료 분산용으로 L2 TTL에 0~60초 jitter도 더했습니다. (결정 12)

### Q. 캐시와 DB가 불일치하면 최대 얼마나 가나요?
TTL이 불일치 상한입니다 — L1 60초, L2 10분+jitter. 능동 무효화(커밋 후 L2 delete + pub/sub로 전 인스턴스 L1 evict)가 일반 경로이고, pub/sub는 at-most-once라 유실되면 L1 TTL 60초가 백스톱입니다. evict 직전에 DB를 읽은 스레드가 evict 후 캐시에 put하는 잔여 race도 존재하는데, 정석 해법(버전 비교 put, 지연 이중 삭제)은 범위 밖으로 명시하고 TTL로 수용했습니다. (결정 12)

### Q. 왜 쓰기 시 새 값을 set(write-through)하지 않고 delete 하나요?
동시 쓰기 2건의 set 순서가 역전되면 옛값이 최종 잔류합니다(write-write race). delete는 최악이 "미스 1회 추가"라 실패 모드가 안전한 쪽으로 닫힙니다. 그리고 evict는 반드시 **DB 커밋 후** — `@Transactional` 안에서 지우면 커밋 전 옛값이 재적재됩니다. 그래서 `TransactionTemplate`으로 커밋 시점을 코드에 드러냈습니다. (결정 12, `ProductService.java`)

### Q. 왜 `@Cacheable`(Spring Cache 추상화)을 안 썼나요?
계층 전이(L1→L2→DB)·single-flight·부분 무효화가 추상화 뒤에 숨기 때문입니다. 이 프로젝트의 목적이 "계층 동작을 이해하고 설명"이라 전이가 코드에 그대로 드러나는 명시적 구현을 택했고, 캐시 히트 시 트랜잭션·DB 커넥션을 아예 타지 않는 것도 코드로 확인됩니다. 재사용하려면 일반화가 필요한 게 트레이드오프. (결정 12)

### Q. CDN(L3)까지 확장한다면?
CDN은 코드 안의 계층이 아니라 **앱 앞단에서 HTTP 응답을 캐싱하는 엣지 계층**입니다. `Cache-Control: public, s-maxage` 헤더 추가 + evict에 CDN Purge API 호출이 3번째 무효화 단계로 들어가고, purge 전파 지연 때문에 **CDN TTL이 새로운 불일치 상한**이 됩니다 — L1/L2에서 쓴 "TTL 백스톱 + 능동 무효화" 원칙의 연장입니다. 단 인증 응답·쓰기 API는 캐싱 불가이고, "서버가 1000 TPS를 견딘다"는 이 프로젝트의 측정 목적과는 어긋난다는 점도 함께 말합니다.

## 축 3 — 백오피스 (RBAC + Spring Batch)

### Q. 역할이 enum 단일 컬럼인데, 권한 관리는 어떻게 확장하나요?
지금은 역할 2개(USER/ADMIN)·보호 자원 1종(`/api/admin/**`)이라 Role/Permission 정규화 테이블은 조인 3개짜리 순수 오버헤드입니다. 권한이 리소스 단위로 세분화되는 시점에 테이블 분리 + 메서드 보안(`@PreAuthorize`)으로 전환합니다 — "정석을 몰라서가 아니라 규모에 맞춰 선택했고 전환 지점을 안다"가 답의 핵심. (결정 13, `UserRole.java`)

### Q. JWT는 발급 후 강제 무효화가 안 되지 않나요?
맞습니다. 그 트레이드오프를 알고 만료 1시간으로 피해 상한을 뒀습니다. 세션+Redis면 서버 측 강제 무효화가 되지만 요청마다 세션 저장소 조회가 필요해 고부하 환경과 결이 안 맞습니다. 역할을 클레임에 내장해 인가 시 DB 조회 0회 — 대신 역할 변경이 토큰 만료까지 미반영. 단일 서버라 HS256 대칭키이고, 발급자/검증자가 분리되면 RS256으로 갈 지점입니다. (결정 13)

### Q. 401과 403을 왜 따로 처리했나요?
미인증=401(entry point), 인증됐지만 권한 부족=403(access denied handler)을 명시 분리했습니다 — Spring Security 기본 설정은 둘 다 403으로 뭉개질 수 있습니다. 필터는 무효 토큰에서 응답을 끊지 않고 미인증으로 통과시켜 판정 책임을 인가 단계 한곳에 모았습니다. (결정 13, `SecurityConfig.java`)

### Q. 정산 배치를 같은 달에 두 번 돌리면요?
clearStep(해당 월 정산 삭제) → aggregateStep(재집계) 구조라 잡 전체가 멱등 — 재실행 = 덮어쓰기입니다. upsert 대안은 이번 집계에서 사라진 상품의 잔존 행을 못 지우는 반면, delete-then-insert는 결과를 항상 "이번 실행의 산출물"로 닫아줍니다. JobParameters에 `requestedAt`을 넣어 같은 달도 매번 새 JobInstance로 실행됩니다(Spring Batch는 동일 파라미터 COMPLETED 잡 재실행을 막으므로). (결정 14, `SettlementBatchConfig.java`)

### Q. 왜 집계를 애플리케이션이 아니라 DB(GROUP BY)에서 하나요?
주문 수백만 행을 앱으로 끌어와 합산하면 전 행이 앱을 통과하고 합산 상태를 스텝 재시작 간 유지해야 합니다. GROUP BY로 리더 입력을 "상품 수" 규모로 줄이면 청크 모델과 자연스럽게 맞습니다. 리더는 `JdbcPagingItemReader`(sort key = product_id) — 페이지 단위 독립 쿼리라 청크 트랜잭션과 궁합이 좋고 재시작 안전. 청크 100은 입력이 상품 수 규모(수백~수천)라 충분히 짧은 트랜잭션이고, 더 키워 얻을 게 없습니다. (결정 14)

### Q. Spring Batch가 cron 스크립트 대비 뭐가 다른가요?
cron은 "언제"(트리거), Spring Batch는 "어떻게"(실행 프레임워크)를 담당하는 별개 레이어입니다. Batch가 주는 건 ① 청크 단위 트랜잭션(대량 데이터를 단일 트랜잭션으로 안 묶음), ② JobRepository 메타데이터(무엇이 어떤 파라미터로 어디까지 돌았는지 → 중복 실행 방지·실패 지점 재시작), ③ 잡/스텝 구조화. 이 프로젝트는 cron 없이 ADMIN API가 트리거이고, 스케줄이 필요해지면 `@Scheduled`나 외부 스케줄러에서 같은 `JobLauncher.run()`을 부르면 됩니다. (결정 14)

## 축 4 — 부하테스트 (k6, 1000 TPS)

### Q. 1000 TPS가 MySQL 1000 TPS라는 뜻인가요?
아니요, **웹 계층 HTTP 처리량**(조회 80% + 주문 20% 혼합)입니다. 핵심은 오히려 그 부하가 MySQL에 도달하지 않게 한 것 — 조회 800/s는 L1/L2 캐시가 흡수하고(히트 시 DB 커넥션 자체를 안 탐), 주문 200/s는 Kafka로 완충 후 배치 INSERT로 묶입니다. MySQL이 받는 트래픽은 1000보다 훨씬 적고, 그게 설계의 목적입니다.

### Q. coordinated omission이 뭐고 왜 오픈 모델을 썼나요?
closed 모델(VU 고정)은 서버가 느려지면 요청 발생도 같이 느려져 수치가 낙관됩니다 — 느린 응답이 다음 요청을 지연시켜 측정에서 누락되는 게 coordinated omission. "초당 1000건이 들어올 때 버티는가"를 물으려면 도착률을 서버 상태와 무관하게 유지해야 하므로 constant-arrival-rate(오픈 모델)를 썼습니다. (결정 6)

### Q. 풀 튜닝은 뭘 했나요?
결론은 "전부 기본값/기존값 유지"입니다. Tomcat 스레드 100/200/400을 같은 절차로 비교했는데 p95가 전부 런 간 편차 밴드 안에 겹쳐 스레드 수는 결정 변수가 아니었고, HikariCP는 부하 중 active/pending 연속 샘플링이 전부 0이라 병목인 적이 없었습니다. **수치가 정당화하지 않는 튜닝 값을 설정에 박지 않는다** — 박는 순간 근거 없는 마법 숫자가 됩니다. (결정 15)

### Q. 측정의 한계는요?
부하기·앱·DB가 같은 머신이라 절대값은 보수적으로 보고, 비교는 같은 세션 안에서만 합니다. 일 단위 환경 편차가 튜닝 효과보다 컸던 것도 측정으로 확인했습니다. 한계를 먼저 말하는 게 신뢰를 줍니다. (결정 15, benchmarks.md)

## 공통 — 아키텍처·회고

### Q. 왜 MSA가 아니라 모놀리식인가요?
데모의 목적이 "기술 포인트 실증"이지 운영 가능한 MSA가 아니기 때문입니다. 단일 앱이면 실행·부하측정·디버깅이 단순하고 4축을 한 프로세스에서 보여줄 수 있습니다. 다만 **모듈러 모놀리식** — 도메인별 패키지(`order`/`product`/`backoffice`/`common`)로 경계를 잡고 Kafka 토픽으로 논리 분리해 뒀습니다. (결정 2)

### Q. MSA로 간다면 무엇이 달라지나요?
서비스 경계는 이미 패키지 경계와 일치합니다(order / product / backoffice). 달라지는 것: ① 정산 프로세서가 `ProductRepository`를 직접 조회하는 도메인 간 의존이 API 호출 또는 데이터 복제로 바뀌고, ② 공유 MySQL이 서비스별 DB로 분리되며(조인 불가 → 정산의 GROUP BY 집계 위치 재설계), ③ JWT가 HS256 대칭키 → RS256 공개키 검증으로(발급자/검증자 분리), ④ L1 무효화 pub/sub은 서비스 내부 관심사라 유지, ⑤ 게이트웨이·서비스 디스커버리·분산 추적이 새로 필요합니다. "경계는 준비됐고, 분리 비용이 정당화되는 시점(독립 배포·팀 분리 필요)에 간다"가 답의 골격.

### Q. 이 프로젝트로 무엇을 얻었나요?
기능 구현이 아니라 **측정과 트레이드오프 판단**입니다. ① 병목은 추측이 아니라 측정으로 — 스레드 4배(2.4×)보다 I/O 배치화(10×+)가 답이었던 경험. ② 캐시는 넣는 것보다 비우는 게 어렵다 — stampede/jitter/멀티 인스턴스 무효화를 각각 왜 그 방식으로 풀었는지 decisions.md에 근거를 남기는 습관. ③ 비동기는 응답을 빠르게 하는 대신 정합성 책임이 생긴다 — 202와 함께 orderKey 폴링·멱등 키를 같이 설계. ④ 측정 방법론 자체(오픈 모델, 워밍업 고정, 환경 편차 인지).

### Q. 가장 아쉬운 점 / 다시 한다면?
정직하게 한계를 골라 말합니다 — 예: "fire-and-forget의 유실 창은 운영이면 Outbox로 닫아야 하고, DLQ 재처리 도구가 없으며, 부하기와 앱이 같은 머신이라 절대값 신뢰도가 낮습니다. 다시 한다면 측정 환경 분리를 먼저 하겠습니다." 한계를 모르는 것처럼 보이는 게 최악, 먼저 말하는 게 최선.
