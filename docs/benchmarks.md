# 부하테스트 결과 (Benchmarks)

> 측정한 것만 기록한다. 검증 안 된 수치 금지. (프로젝트 원칙)
> 각 측정마다: 환경 / 시나리오 / 수치(TPS·p50·p95·p99·에러율) / 병목 / 개선.

## 측정 환경 (공통)
- 머신: Intel i7-9700K (8C/8T), RAM 32GB, Windows 11 Pro
- 인프라: Docker Compose — MySQL 8.0(3307), Redis 7(16379), Kafka 3.8.1(KRaft 단일 노드)
- 앱: Java 17, Spring Boot 3.5.14, HikariCP max-pool=20, Tomcat maxThreads=200(기본값)
- 부하도구: k6 v2.0.0, **오픈 모델(constant-arrival-rate)** — 서버가 느려져도 도착률 유지 (coordinated omission 회피)
- ⚠️ **한계**: k6 + 앱 + Docker가 **같은 머신**에서 동작 → 절대 수치보다 상대 비교(동기 vs 비동기)가 목적

## 측정 1-a. 주문 동기 버전 기준선 (2026-06-10)

시나리오: `POST /api/orders` (단일 INSERT 트랜잭션), 도착률 고정 30초씩. 스크립트: `load-test/order-sync-baseline.js`

|---|---|---|---|---|---|---|---|---|
| 100/s | 100.0 | 12.8ms | 12.1ms | 15.1ms | 17.0ms | 86ms | 0% | 0 |
| 500/s | 499.8 | 24.8ms | 16.2ms | 31.4ms | 59.8ms | 619ms | 0% | 0 |
| 1000/s (1차) | 989.0 | 161ms | 129ms | 355ms | 435ms | 2.0s | 0% | 0 |
| 1000/s (2차) | 986.1 | 224ms | 159ms | 526ms | 626ms | 1.9s | 0% | 68 |
| 1000/s (3차, 메트릭 샘플링 병행) | 903.4 | 1.13s | 1.17s | 1.53s | 1.63s | 2.8s | 0% | 1,497 |
| 1000/s (**콜드 스타트** 직후) | 771.5 | 2.23s | 2.12s | 2.91s | 3.14s | 4.6s | 0% | 5,321 |

### 결과 해석
- **1000 TPS 자체는 도달** (실측 986~989 req/s, 에러 0%). 단, p95가 17ms(100/s) → 435~626ms(1000/s)로 **약 30배 열화** — 처리량은 버티지만 큐잉이 심함.
- **콜드 스타트의 영향이 매우 큼**: JIT 워밍업 없이 풀부하 진입 시 p95 3.14s, 도착률 23% 미달(min조차 1.55s — SYN 재전송/accept 백로그 오버플로 패턴). → **측정 전 워밍업은 필수 절차**로 고정.
- **런 간 편차가 큼**(1000/s에서 p95 435ms~1.63s): 단일 머신에 부하기·앱·DB 동거 + 이전 런의 TIME_WAIT 소켓 누적 영향으로 추정. 비교 측정 시 동일 순서·동일 워밍업으로 통제할 것.

### 병목 분석 (측정 근거 기반)
| 증거 | 수치 | 해석 |
|---|---|---|
| CPU (1000/s 2차 중 샘플링) | 평균 14%, 최대 27% | **CPU 병목 아님** |
| HikariCP active/pending (3차 중 1초 간격 25회) | 전부 0 | **DB 커넥션 풀 병목 아님** — INSERT 자체는 sub-ms로 추정 |
| 서버측 누적 평균 (`http.server.requests`) vs 클라이언트측(3차) | 228ms vs 1.13s | 차이 ≈ 0.9s가 **서블릿 필터 밖**(Tomcat 큐·accept 백로그) 대기. 서버 내부 228ms도 DB 대기가 아니므로 스레드 스케줄링/락 의심 |
| 동시 in-flight ≈ 실측 900/s × 0.228s ≈ 205 | Tomcat maxThreads=200과 일치 | **워커 스레드 풀 포화**가 1차 병목 후보 |

- **미확정**: 워커 스레드가 DB 대기도 CPU도 아니면서 ~200ms를 소모하는 지점. 후보: Docker Desktop 포트 프록시(loopback→컨테이너) 경유 비용, GC, Hibernate 내부.
- **다음 실험**: (1) `server.tomcat.threads.max` 변화(100/200/400)로 p95 반응 확인, (2) `management.metrics.distribution.percentiles-histogram`으로 서버측 p95 직접 노출, (3) MySQL을 호스트 네이티브로 바꿔 Docker 프록시 영향 분리.

스크립트: `load-test/order-async.js`. 절차: 워밍업(100/s 30초, 기록 제외) 후 100 → 500 → 1000 → 1000 순서, 각 30초.

- 동기 교차 측정이 1-a(986~989/s, p95 435~626ms)보다 나쁨. 후보: orders 테이블 증가(7.5만→21만 행 + order_key 유니크 인덱스 추가), 같은 프로세스에 Kafka 컨슈머 동거, 직전 비동기 런의 소켓 잔여. **1-a에서 기록한 런 간 편차 범위(p95 0.4~1.6s)와 겹치므로 "동기는 1000/s에서 수백 ms~수 초 큐잉"이라는 결론은 유지.**

### 결과 비교 (1000/s 기준)
| 버전 | 실측 TPS | p50 | p95 | 에러율 | drop | 병목 |
|---|---|---|---|---|---|---|
| 동기 | 828~989 | 129ms~1.91s | 0.44~2.55s | 0% | 0~3,484 | Tomcat 워커 풀 포화 (요청 경로의 DB INSERT) |
| 비동기(Kafka) | **1000.0** | **0.53ms** | **1.34~1.56ms** | 0% | **0** | 접수 경로는 여유. **컨슈머 ~200건/s가 병목** |

### 결과 해석
- **가설 검증됨**: 요청 경로에서 DB INSERT를 빼자(브로커 ack 비대기 발행만 수행) p95가 수백 ms~초 → **1.3~1.6ms**로 떨어지고, 1000/s에서 도착률 100% 달성(drop 0). 동기가 in-flight ≈ 200(워커 풀 한계)에서 큐잉하는 동안, 비동기는 요청당 점유 시간이 sub-ms라 같은 워커 풀이 전혀 포화되지 않음.
- **단, 처리량 부채가 컨슈머로 이전됨**: 컨슈머 처리율 ≈ **183~202건/s** (파티션 3 × 컨슈머 3스레드). 1000/s × 30초 백로그(3만 건) 소진에 ~120초. "접수 1000 TPS"와 "처리 1000 TPS"는 별개 — 면접 포인트.
  - 컨슈머 이벤트당 ~15ms 소요(3스레드 × ~66건/s). 구성: existsByOrderKey SELECT + INSERT + 개별 트랜잭션 커밋(fsync) + Docker 포트 프록시 왕복.
  - **개선 후보(다음 실험)**: 배치 리스너 + JDBC batch INSERT(`rewriteBatchedStatements`는 이미 켜져 있음), 파티션·concurrency 증가, exists 검사 제거(유니크 제약 + 중복 무시로 SELECT 1회 절약).
- **정합성 확인**: 부하 후 orderKey 보유 주문 81,009건 = DISTINCT 81,009 = COMPLETED 81,009 (중복 0). 부하 중 DLQ 유입 0건 (DLQ 오프셋 1은 통합 테스트 주입분).
- **한계**: 비동기 202는 "브로커에 닿기 전" 유실 가능성을 남긴 측정(decisions.md 7번). 동기와 비동기는 응답이 보장하는 내용 자체가 다름(저장 완료 vs 접수 완료) — 수치 비교 시 이 전제를 같이 말해야 공정.

## 측정 1-c. 컨슈머 처리량 개선 실험 (2026-06-10)

1-b의 병목(컨슈머 ~200건/s)을 두 가설로 나눠 검증한다.
- 가설 A: 스레드 수 부족 → 파티션 12로 증설 후 concurrency 3/6/12 비교.
- 가설 B: 이벤트당 개별 트랜잭션(커밋 fsync + 왕복 3회)이 본질 → 배치 리스너 + JDBC batch INSERT.

절차는 1-b와 동일(워밍업 100/s 30초 → 1000/s 30초 + 드레인). **처리율 = 30,000건 ÷ (부하 30초 + 드레인)**.

### 1-c-i. 동시성 스케일 (파티션 12, 레코드 단위 컨슈머)
| concurrency | 드레인 | 컨슈머 처리율 | 배율(vs 3) | 접수 p95 |
|---|---|---|---|---|
| 3 (재기준) | 124s | ~195건/s | 1.0× | 1.87ms |
| 6 | 61s | ~330건/s | 1.7× | 2.62ms |
| 12 | 33s | ~476건/s | 2.4× | 4.68ms |

- 파티션 3→12 증설 자체는 영향 없음 (concurrency 3에서 1-b와 동일한 ~195건/s).
- 스레드 증가로 늘긴 하지만 **선형 미달**(12스레드에서 2.4×), 12스레드로도 1000/s에 한참 못 미침.
- 부작용: 컨슈머 스레드가 늘수록 **접수 경로 p95가 1.87 → 4.68ms로 열화** — 같은 프로세스/DB를 두고 경합.
- 결론: 가설 A 기각에 가까움. 이벤트당 고정 비용(개별 트랜잭션 커밋)이 지배적 → 가설 B로.
